## 結論（先に）

**条件付きで採用を支持する。** ハーネスは「何も無い」より明らかに良い。
ベンチマークの再実行による改ざん検出、追記専用、自己レビューの拒否、
レコードとコミットの束縛（R5）は**実際に効いていた**。

ただし **「pass」は「8 つの要求検査が通った」という意味であって、「完全」ではない。**
git レイヤの強制には迂回可能な抜け道が 2 件（F1・F2）、main への着地ゲートは
そもそも動いていない（F3）。**F1〜F4 を閉じる別提案（PRP-002）が承認されるまでは、
main へのマージという人間のゲートが唯一の実効的な防護線であり続ける。**

### 効いていたもの

- **R4 追記専用**: 既存行の書き換え・state ファイルの削除を検出
- **R2 パス権限（単体コミット）**: verifier が `scripts/` や `state/claims.jsonl` を触ると FAIL
- **R3 分離**: 自己レビュー・自己承認・レビュアーの兼務承認を状態レイヤで拒否
- **R5 authorship 束縛**: 他人のセッション名義のレコードを `git blame` で検出
- **R1 の一部**: トレーラ欠落・未所持ロール・`Informed-By` の祖先違反を検出
  （実際、本セッションの `Informed-By: HEAD` という誤記も検出された）
- **ベンチマーク再現性**: 手書き成果物という 2026-10-19 の失敗は再現不能

### 効いていなかったもの

| ID | 重要度 | 内容 |
| :--- | :--- | :--- |
| **F1** | High | `Session-Id` は自己申告。ブランチとの束縛は **HEAD コミットでしか検査されない**ため、他人のセッション（最悪 `bootstrap`）を名乗るコミットを履歴に埋められる。実証: ガード自身を無効化した状態で `check-all` が `ok: true` |
| **F2** | High | マージコミットは `is_merge` で読み飛ばし、`--first-parent` は側ブランチを見ない。実証: `scripts/` と `.github/` をトレーラ無しコミットで着地させても `check-all` は `ok: true`（R2 と R6 の迂回） |
| **F3** | Medium | CI の land ゲート `check-commits --stage land` は **CLI 引数として存在せず exit 2**。プログラムから呼んでも、merge commit なら検査対象 0 件で空振り、squash なら 59 件の誤ったエラー |
| **F4** | Medium | `researchos_session.py close` を自分のセッションに使うと `session ... is closed` でガード違反。**ドキュメント記載のコマンドが実行した瞬間に自分を壊す** |
| **F5** | Low | キューの `required_checks`（`governance_review` ほか）はレビュー結果と突き合わせられない。しかも `governance_review` という検査は存在しない（相当するのは `policy`） |
| **F6** | Low | verifier は `gitswarm/artifacts/readout_snapshot.json` を書き換えられるため、`readout_snapshot` 検査は「最後の再ベースライン以降ドリフトなし」しか証明しない |

## 提案された次の一手（PRP-002 のたたき台）

私は verifier なので `scripts/` に触れない（R2）。以下は**次の proposer セッションへの
提言**であって、実装ではない。

1. **ブランチ束縛を HEAD だけでなく全コミットに適用する**（F1）。
   継承コミットについては「そのセッションのブランチの祖先であること」を
   `git merge-base --is-ancestor` で確認する、などの形が考えられる。
2. **マージコミットを検査対象に戻す**（F2）。`is_merge` で `continue` するのでなく、
   マージコミットについては「第1親との差分にガバナンスパスが含まれていないこと」か
   `Governance-Proposal` トレーラーを要求する。
3. **`--stage` を CLI に定義する**（F3）。`land` は main の push でだけ意味を持つので、
   squash を前提にするなら「PR 全体を 1 コミットとして扱う」別の判定が必要。
4. **`close` の出口を用意する**（F4）。close コミット自身を検査対象から外すか、
   close を state 変更ではなく次のセッションの開始時に記録する。
