## 4. 判定規則への照合

設計 §11 の採用条件（**すべてを満たす場合に3分割を既定にする**）に、§2の実測を当てはめる。数値はすべて提案値であり、D2での確定記録は本報告では確認できていない（§6-2）。

| 条件 | 提案閾値 | 実測 | 判定 |
|---|---|---:|---|
| (i) M1：並行の壁時計が単一の0.70倍以下 | ≤0.70 | 4.25倍（代理値） | **不成立** |
| (ii) M3：事実誤りの件数差が+2件以内 | ≤+2 | 0件 vs 0件（差0） | 数値上は成立。ただし両アーム0件で**判別不能** |
| (ii) 未回答（棄権＋欠落）の件数差が+2件以内 | ≤+2 | 0件 vs 0件（差0） | 成立 |
| (iii) M2：並行の総セッション時間が単一の1.5倍以内 | ≤1.5 | 5.07倍 | **不成立** |
| (iv) M4：手直しが真値確定項目の1割未満、構造的崩壊なし | <5.1件 | 0件、崩壊なし | 成立（人間介入は4対1） |

## 5. 「次からどちらの運用を既定にするか」への含意

### 5.1 含意

**本研究の抽出型タスク（1本の論文から51項目を抜く形）については、次回も単一ワーカーを既定とする。**

理由は、事前登録した判定規則の時間条件が両方とも大きく不成立だったことにある。単一は約3分20秒のセッションで51項目を終え、並行は合計約17分（壁時計では約34分）を要した。この規模のタスクでは、3分割の調整コスト（3回の投入、開始コミット管理、停止・再指示、PRの直列マージ）が、分担による短縮を上回った。

### 5.2 この結果が言えないこと

- **「3分割は一般に劣る」とは言えない。** 試したのは、設計 §6 が定めた「層化配分で各ワーカーが全文を航行する」モード1回だけである。実務でよくある「節ごとに読む範囲を分ける」モードは試していない。設計 §12 も、この配分では壁時計の利得が過小に出ると事前に述べている。
- **「並行アームのワーカーが遅い」とも言えない。** P3は17項目を112秒（項目あたり6.6秒）で終えており、単一の3.9秒/項目に近い。P1・P2の項目あたり時間が大きいのは、担当確認待ち・停止/再指示待ちを含むためである。ボトルネックは抽出そのものより、投入と調整の直列性にあった。
- **「誤り率に差がない」とは言えない。** 両アーム0件で、誤りが観測できる難度ではなかった。51項目に増やしても、明示値のルックアップ中心では誤り信号が増えないことが分かった（前回の8項目0件の再現）。
- **モデル差は分離できない。** 4セッションの基盤モデルはArena上で統制できず、すべて `unknown`。アーム間差にはモデル個体差が交絡しうる。

### 5.3 再実験するなら

1. **開始コミットを1つに固定し、どのアームの出力も含まないコミットから4セッションを立てる**（§6-1の汚染を防ぐ）。
2. **プロンプト投入時刻を人間が記録する**（設計 §13.2 を空欄のまま渡さない）。
3. **誤りが出る項目集合にする**：推論・突合・曖昧な表記・PDF由来の数値など、ルックアップでない項目を混ぜる。あるいは項目数を増やすのではなく、1項目あたりの判断難度を上げる。
4. **範囲分割モードと層化配分モードを分けて測る**。本実験は後者だけ。
5. **D2の承認記録を独立に残す**（設計書の状態欄を「承認済み」に更新するか、D2記録文書を作る）。
6. **赤いCIのPRをマージしない**。実験中にfixtureを直す必要があるなら、実験を止めて直し、全アームを同じゲート版で再走させる。

## 6. 実験運営の失敗（率直な記録）

### 6.1 開始コミットが共通でなく、後発アームのツリーに先行アームの出力があった（最重要）

設計 §7.2 は「両アームの全セッションは同一の base コミットから開始する」と定める。実際の `base_commit` は4つとも異なった。

| ワーカー | base_commit | 予定との関係 | そのツリーに含まれる他アームの成果物 |
|---|---|---|---|
| S | `58d5f28` | 予定より前（S自身のPRマージ前） | なし |
| P1 | `ccf76aa` | 予定の共通開始コミット（= PR #58 のマージ） | **S の JSON/MD** |
| P2 | `2411524` | `ccf76aa` の7コミット子孫 | **S の JSON/MD** |
| P3 | `91a08f4` | `ccf76aa` の13コミット子孫（= PR #61 のマージ） | **S・P1・P2 の JSON/MD** |

- `git ls-tree` で確認：`ccf76aa` と `2411524` は `contributions/2026-10-21_svm_single.json` を含み、`91a08f4` は single・p1・p2 の3アーム分を含む。
- 各ワーカーは「他アームの成果物の内容は見ていない」と自己申告している（P1はゲートの自動走査でファイル名と引用検査結果のみ、P3はfixtureの注記と `git diff --name-status` でファイル名のみ、P2は参照なしと明記）。しかし**自己申告を機械的に検証する手段はなく、ツリーにファイルが存在したこと自体は事実**である。P3は特に、直前のP2の出力を含むコミットから開始している。
- したがって、並行アームの正解率を「独立に抽出した結果」として扱うことはできない。本報告を**参考報告**とする理由がここにある。設計 §7.3 の「手順逸脱が起きたセッションがある場合、結果の格を人間の判断に上げる」に従い、格の判断を人間に委ねる。
- 予定の共通開始コミット `ccf76aa` 自体がSの出力を含んでいたことも問題である。共通開始点は「どのアームの出力も含まないコミット」でなければならない。

### 6.2 D2承認の独立記録がない

設計はD2（人間による項目表・指標・判定規則の承認）を前提とするが、設計書の状態欄は「提案」のままで、D2の記録文書はない。唯一の証拠は `contributions/2026-10-21_scoring_tool.md` の「この実装セッションで人間に確認し、現行設計を承認して進めるを選択した」という**伝聞**である。各ワーカーも「独立したD2承認記録は確認していない」と述べている。事前登録の錨としては弱い。

### 6.3 人間の壁時計記録がなく、M1が測れていない

設計 §13.2 の表は空欄で、X4プロンプトにも投入時刻・介入回数の記録が貼られていない。M1は「人間が記録する」指標であり、**定義どおりには測定できていない**。本報告の4.25倍はセッション開始時刻を代理にした値で、プロンプト読解・投入準備の時間を含まない。M1を主指標にした判定は、次回は記録なしでは行えない。

### 6.4 CIが赤のまま2本のPRがマージされた

- PR #58（単一）は 08:37:21Z、PR #59（P1）は 08:52:59Z にマージされたが、いずれも `core-check` は **fail**（unittest 3件、check_memo_citations 失敗）。原因は、固定版一次資料 `2609.37633` がオフライン書誌スナップショットに未収録だったこと。
- 両ワーカーは「CIが赤の間は自己マージしない」と明記していた。実際のマージは同一アカウントで行われ、実行者は特定できない。自律マージ方針 §2 の「CIが緑であること」に反する。
- PR #60（fixture追加）が 08:53:21Z にマージされ、以降のゲートは緑になった。つまり**実験の途中でゲート環境が変わった**。S・P1は旧環境、P2は移行期、P3は新環境でゲートを走らせている。

### 6.5 ゲート環境がアーム間で揃っていない

各PR本文のゲート実測は、S「303テスト中3失敗」、P1「349テスト中3失敗」、P2「388テスト中3失敗」、P3「388テスト中0失敗」。テスト総数と失敗数が異なる。P3のbaseにはゲートスクリプトの変更が含まれ、P3自身も「当初の共通開始時点とは異なるスクリプト版で走っている」と記録している。抽出値そのものへの影響は考えにくいが、**同条件性の一部が崩れている**。

### 6.6 P3の前回試行（09:04:27Z）の停止理由が不明瞭

P3は前回の投入で「開始HEADの不一致と**同一担当列の成果物の既存**」を理由に抽出を開始せず停止した（7ツール呼び出し、成果物なし、ゲート未実行）。しかし前回試行の時点で、P3の成果物は `main` にもPR一覧にも存在しなかった（現在の `main` にあるP3の成果物は本実行のものである）。「同一担当列の成果物」が何を指したのかは記録から特定できない。別ブランチの残骸、あるいは誤認の可能性がある。**見た可能性のあるファイルの身元が不明**であり、汚染の評価を難しくしている。

### 6.7 項目設計が誤り信号を生まなかった

51項目に増やした設計意図は「真値確定項目が約40件残れば誤り率数%でも観測できる」だった。実際は51件すべて真値確定できたが、**両アームとも0件の誤り**だった。項目の大半が表セル・明示数値・逐語引用で、一次資料のHTMLも明瞭だったため、丁寧に全文を読めば誰でも正解できるルックアップ課題になっていた。設計 §12 が警告した「項目選択の偏り（見つけやすい項目に寄る）」が現実化した形である。項目数を増やすだけでは誤り信号は増えない。

## 7. 限界

- **パイロット1回**：各アーム1回の観測であり、統計的検定はしない。件数と比で述べる。観測された差がアームの違いによるものか、ワーカー個体・時間帯・運営の違いによるものかは分離できない。
- **同条件性の破れ**：§6-1のとおり、開始コミットが共通でなく、後発アームのツリーに先行出力があった。厳密な同条件比較ではない。
- **M1未測定**：人間の投入時刻記録がなく、代理値のみ。M1を主指標にした断定はできない。
- **M3の天井効果**：両アーム0件で、誤り率の差を検出できない。項目を難しくしない限り、この設計では誤り比較が成立しない。
- **モデル交絡**：基盤モデルの同一性を統制できず、すべて `unknown`。
- **配分の人為性**：層化のため各Pワーカーが全文を航行する。範囲分割モードの性能ではない。
- **取得経路**：HTML v2 のみ。PDF原本や別版での難しさは測っていない。HTMLの数値二重描画（Q33等）は本文照合で解消したが、経路依存の難しさは残る。
- **ログの自己申告性**：`tool_calls` と `files_read` は自己申告で、検証できない。M2・副次指標は目安。
- **真値のスポットチェックなし**：X4が単独で確定した。設計 §8.5 の人間確認は未実施。
- **rhoは目的外**：共通誤り0件は相関の証拠ではなく、件数の事実。相関誤りの推定には踏み込まない（凍結中の議論を再開しない）。

## 8. 台帳への提案（実施はしない）

コード・`state/` は変更していない。以下は提案のみ。

1. **論文SRCの登録は、必要になったときに行う**。今回の実験でarXiv:2609.37633v2を読んだが、実験のための一時利用であり、リポジトリの文献クレームに使う予定がない限り、SRCを増やす必要はない。登録するなら `type: "preprint"`、title、9名の著者、year 2026、url `https://arxiv.org/abs/2609.37633`、venue `arXiv:2609.37633v2 (cs.LG), last revised 2026-10-19`、DOI `10.48550/arXiv.2609.37633` を提案する。

3. どうしても内部実験を記録するなら、`type: "report"` のSRC（urlは本メモのリポジトリ内パス）＋EVD（excerptは§2のM1/M2/M3表の要約、`data_points` に 51/51/0、485秒/2,062秒、200秒/1,014秒、confidence `low`）＋「この1回のパイロットでは3分割が壁時計を短縮しなかった」に限定したCLAIM、という形が最小だろう。ただし**先に§6-1の汚染を解消した再実験を行うことを推奨する**。その場合は実行前に仮説と判定規則を登録し、投入時刻を記録すべきである。
4. 運用手順への提案（台帳外）：プレイブックに「実験用の共通開始コミットは、どのアームの出力も含まないコミットを選ぶ」「CI赤のPRは実験出力として固定しない」の2項を追加する。
