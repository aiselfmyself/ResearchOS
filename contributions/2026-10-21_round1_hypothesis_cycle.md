## 2. ゲートが実際に捕まえたもの

**3 件。いずれも記録の欠落であり、内容の誤りではない。**

1. **`validate_state.py`（ゲート4）**——仮説・検索・実行の各レコードが本メモのパスを
   参照していたが、メモを書く前だったため「存在しないパス」として 3 件のエラーが出た。
   本メモを先に作る順序に変えて解消した。
2. **`check_memo_ledger_refs.py`（ゲート7）**——本メモが Phase 2 で追加予定の
   `next_queries.py` を `scripts/` 付きのパスとして書いていたため dangling になった。
   「未作成のファイルを、現存する成果物のように参照する」経路を塞ぐ仕様どおりである。
   予定であることが分かる表記に変えて解消した。
3. **既存テスト（`tests/test_minimal_core.py`）**——新しい EVD に `quote_type` が無く、
   `test_every_evidence_declares_quote_type` が赤になった。スキーマではなくテストが
   保持している規約であり、**schema だけ見て新レコードを書くと落ちる**。`verbatim` を付けて解消した。

これは**ゲートが設計どおり効いた初めての実データでの実例**である。Phase 1 のテストは
合成データで赤くなることを固定していたが、実データで「書き忘れ」を捕まえたのは今回が初めてだった。
なお、捕まえたのは参照の欠落であって**内容の誤りではない**（Phase 1 のゲートの限界は §4）。

## 3. 摩擦（ここが本稿の主目的）

必須項目のうち **4 つが実作業に合わなかった**。いずれも「記録を増やす」方向ではなく
「記録の形が現実と違う」という種類である。

### 3-1 `next_observations` の大半が「文献で探せる問い」になっていない

既存 4 仮説の `next_observations` を実際に読むと、**内部測定**ばかりである。

| 仮説 | 書かれている「次に集める観測」 | 種別 |
|---|---|---|
| `HYP-20261021-9f99` | 3 水準以上のモデル群×3 種以上のハーネスの直交要因実験 | 自前実験（**ID 18 で凍結**） |
| `HYP-20261021-fee7` | リーク審査と δ 正則化を個別に外した統制アブレーション | 自前実験 |
| `HYP-20261021-4cdb` | `gap_scan.py` 運用前後での unexplained 比率の推移 | 内部計測 |
| `HYP-20261021-a10b` | 全文脈保持と剪定＋DAG 分解の反復比較 | 自前実験 |

**1 件も「文献検索で埋められる問い」になっていない。** したがって Phase 2 の
`next_queries.py`（S7）を作っても、**入力が空同然でクエリが生成できない。**
今回のラウンドでは、この 4 件を無視して手でクエリを書いた。

**提案**：`next_observations` を 2 つに分ける。

- `next_literature_questions`（文字列の配列。検索クエリに変換できる問い）
- `next_internal_measurements`（文字列の配列。自リポジトリで測るもの）

Phase 1 のゲートは「`next_observations` が非空」しか見ていないので、
**中身が検索可能かを検査していない。** これは Phase 2 の前提を壊す欠陥であり、
Phase 2 着手前に直すべきである。

### 3-2 台帳の外の観測に ID が無い

今回の検索の動機は「新規 4 仮説の支持の 94〜100% が生成元」という**ラウンド0の測定**である。
しかしその測定は `docs/2026-10-21_hypothesis-cycle-automation.md` §2.3 の表にしか存在せず、
**台帳の ID を持たない。** そのため `QRY-20261021-8da2.derived_from` を空にせざるを得なかった。

`derived_from` は「台帳の穴に紐づかないクエリは採用しない」という S0 の規律を支える欄なので、
空が常態化すると規律が形骸化する。

**提案**：計測器の出力も EVD にする。`SRC-004`（本リポジトリのコード）を出典として
`EVD-*` を起票すれば、`derived_from` に入れられる。今回の自己支持率の測定は、まさに
その第 1 号にできる（`SRC-004` は既に 3 件の EVD を持つ）。

### 3-3 既知項目の同定に channel が無かった

`arXiv:2404.13076` は検索で見つけたのではなく、**ID を知っていて取得した**。
既存の enum（`keyword` / `citation` / `review` / `manual`）では `manual`（人間が提示）が
最も近いが、これはエージェントが自分の知識から引いた経路であり、人間の提示ではない。
`manual` と記録すると**経路の記録が嘘になる。**

**対応**：`channel` に `known_item` を追加した（`schemas/search_log.json`）。
これはゲートを緩める変更ではなく、実在する経路を列挙に足す変更である。
**探索（keyword / citation / review）と同定（known_item）を分けた**ことで、
「新規性の源泉が探索にあるか」を後から数えられるようになる。

### 3-4 新しい仮説は、生まれたラウンドで支持を持てない

生成元を支持から外す設計（Phase 1 の中心）は正しく動く。動くのだが、その結果
**`HYP-20261021-00b4` は支持 0 件で生まれる。** 独立した観測が次のラウンドで見つからなければ、
支持 0 のまま残る。

これは欠陥ではなく意図した挙動だが、**ループの設計に 1 つ含意がある**：
支持を増やすには「生成に使っていない観測」を能動的に探すしかない。
つまり S0 は「穴を埋める検索」だけでなく、**「既存仮説の外側を探す検索」**を
一定割合で混ぜる必要がある。そうしないと、支持は永久に増えない。

**提案**：ラウンドごとに検索の最低 1 件を「既存仮説の生成元と引用グラフが重ならない領域」に
割り当てる（設計 §7-2 の 3 系統検索の具体化）。

### 3-5 反証条件は文章で、機械は判定できない

`refutation_condition` は 3 つの文字列（`observable` / `would_refute` / `expected_if_true`）で
必須にしたが、**その条件が満たされたかを判定するのは人間か LLM** である。
Phase 1 のゲートは「書いてあること」しか見ていない。

機械が判定できる半分は `PRD`（予測）側にある。`PRD-20261021-1f70` は
「10 件中 7 件以下」という**数値の閾値**を持つので、次ラウンドで機械的に採点できる。
**反証条件を「予測＋閾値」に落とせたものだけが、実際に反証可能になる。**

**提案**：`refutation_condition` に任意項目 `threshold`（機械可読）を足し、
書けたものだけ `PRD` に昇格させる運用にする。書けない仮説は「反証不能」として
`gap_scan` 系の計測器が数える（ゲートにはしない）。

### 3-6 計測器（`gap_scan`）とゲートの意味論がまだ一致していない

Phase 1 は `derived_from` を**記録する**ところまでで、**集計から外す**実装は Phase 3 の
`self_support.py` に回した。その結果、同じ台帳を 2 つの道具が違う数で読む。

- `validate_state.py` は「`derived_from` が付いているか」を見る（支持件数は数えない）。
- `gap_scan.py` は verdict をそのまま数えるので、**新仮説の支持を 3 件と表示する**。
  うち 3 件はすべて生成元である。

**これは無害ではない。** 台帳の読み手が `gap_scan` の数字をそのまま引用すると、
Phase 0 で測った「自己支持 94〜100%」を**このラウンドで再生産する**ことになる。
数字は正しくても意味が逆になる典型例である。

**提案**：`gap_scan` に `--exclude-derived-from` を足し、既定の表示に
「うち derived_from: N 件」を併記する。実装は Phase 3 の `self_support.py` と同じ計算を使う。
**それまでの間、`gap_scan` の `support` は「verdict が support の関係数」と読み、
支持の証拠数としては引用しない。**

## 4. 今回のラウンドで分かった限界

1. **n=1**。1 周では「ゲートが実作業に合うか」の一部しか分からない。
   特に S2（選別）と S4（裁定）の再現性は測っていない。
2. **`screened` は自己申告**。274 件のヒットのうち 3 件しか読んでいないが、
   それを検証する仕組みは無い。件数は「そう主張した」以上の意味を持たない。
3. **ゲートは内容を検査しない。** 今回捕まえたのは参照の欠落 1 件だけである。
   自己支持の循環（§3-4 の元問題）は、`derived_from` を**正しく付けたか**に依存する。
   付け忘れれば支持が水増しされるが、Phase 1 のゲートはそれを検出しない。
   Phase 3 の `self_support.py` は「付いていない生成元」を推定できないため、
   **`derived_from` の正しさは依然として人間のレビュー対象**である。
4. **所要 11 分・介入 1 回**という数字は、ラウンドの定常コストではない。
   今回は題材選定を既存の測定から引き継いだ。S0 を毎回ゼロから行う場合はより長い。

## 5. Phase 2 に進む前の修正（優先順）

| # | 修正 | 理由 |
|---|---|---|
| 1 | `next_observations` を文献質問と内部測定に分割 | 分けないと S7 が空回りする（§3-1） |
| 2 | 自己支持率などの計測器出力を `EVD`（`SRC-004` 起点）として起票 | `derived_from` を埋められるようにする（§3-2） |
| 3 | `refutation_condition.threshold`（任意・機械可読） | 反証可能な仮説だけを `PRD` に昇格させる（§3-5） |
| 4 | S0 に「既存仮説の外側」検索を最低 1 件混ぜる規則 | 支持 0 から抜ける経路を作る（§3-4） |
| 5 | クエリ生成器 `next_queries.py`（Phase 2 で追加予定） | 上記 1〜4 の後 |

**1〜3 は schema の追加項目であり、既存レコードの書き換えを伴わない。**
ファイル単位の免除（Phase 1）があるため、既存レコードは影響を受けない。

## 6. この 1 周で言えること・言えないこと

**言えること**

- Phase 1 の 3 ゲートは実データで通り、**書き忘れ 1 件を実際に捕まえた**。
- 自己支持を外す設計は動く。新しい仮説は支持 0 から始まる。
- `next_observations` の形が Phase 2 の前提を満たしていないことが、**実データで確認できた**。
  これは設計時に気づけなかった種類の欠陥である（空の台帳では見えない）。

**言えないこと**

- このループが「新しい知見を生む」こと。今回の `HYP-20261021-00b4` は
  **2 論文の対比を整理したもの**であり、どちらの論文にも書かれていない結合ではあるが、
  新規性の水準は未評価である。
- 自動化率の改善。1 ラウンドでは基準値が無い（`runs` が 1 件しかない）。
- 自己選好が**本リポジトリの裁定で実際に起きている**こと。今回の EVD は
  「他所で起きる」ことの証拠であり、自リポジトリでの測定は `PRD-20261021-1f70` が
  次ラウンドに課している。
