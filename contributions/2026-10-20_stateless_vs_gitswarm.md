# 文献調査メモ：Stateless Harness と GitSwarm

- 作成日：2026-10-20
- 対象：`task/TASK.md` §1「自律型AIエージェントにおける長期推論・分散協調アーキテクチャ（Stateless vs GitSwarm）の学術文献調査」
- 位置づけ：arXiv プレプリント3本の調査メモ。新しい実験は行っていない。実行した確認は §7 に列挙する。

## 1. 結論

- Stateless Language Agents（SLA）[1] と GitSwarm [2] は、いずれも「エージェントの会話の外に研究状態を置く」設計である。対立軸は状態の有無ではなく、**状態の置き場所・決定の集中度・検証の方法**にある。
- SLA は harness が候補解と測定結果を所有し、stateless な Advisor が実験を割り当てる。GitSwarm は共有 Git リポジトリを記憶とし、同質ワーカーが自律的に次を決める。
- 共通の弱点は評価の質である。GitSwarm 自身が、検証可能な課題では推薦多数決を外して検証性能で選ぶと明記している。多数決は真理の判定器ではなく、検証不能時のフォールバックである。
- 現時点の一次資料では優劣は決着しない。ベンチマーク・モデル・計算予算が異なり、両者を直接比較した実験が存在しない。

## 3. 二つの設計

### 3.1 Stateless Language Agents（SLA）[1]

「stateful search with stateless agents」を掲げ、エージェントは呼び出し間で会話を持ち越さない。harness が研究状態（候補解と測定結果）を所有し、呼び出しごとに役割特化の文脈を再構成する。stateless な Advisor が harness の要約した証拠を読み、並列 Worker に具体的な実験を割り当てる。

評価はソフトウェア工学・カーネル最適化・アルゴリズム設計、最大10億トークン。全タスクで最良の最終結果を報告し、カーネルでは最強ベースラインの最終性能に 84% 以上少ないトークンで到達した。Advisor の消費はトークンの 0.6% 未満である。

### 3.2 GitSwarm [2]

「compounding inference」を掲げ、推論時間の計算を個別の軌跡ではなく、永続的に再利用できる作業の集積として組織する。非同期的な同質ワーカーが、共有・分岐可能な Git リポジトリ上で explore / experiment / verify / refine / synthesize する。アトミックコミットが中間成果物を残し、`informed_by=` の意味的依存がブランチを跨ぐ再利用を記録する。中央の知的プランナーはおらず、harness がスケジューリングと最終評価（validation）を担う。

評価は IMOProofBench-Advanced（30問全問）、ProgramBench（79.4%、最強ベースライン 65.1%）、ニューラルアーキテクチャ研究3件。ProgramBench では貢献の 94.7% が後続に構築され、選択解の推移的祖先が貢献グラフの 82–93% を覆う。NanoChat の最初の24アクティブ時間では、負と明示された研究コミット 709 件のうち 497 件（70.1%）が後続に引用された（[2] §3.3）。この 70.1% は NanoChat の限定された窓の値で、全タスクの普遍値ではない。

### 3.3 比較

| 軸 | SLA [1] | GitSwarm [2] |
|---|---|---|
| 状態の所在 | harness（候補解＋測定結果） | 共有 Git リポジトリ（履歴） |
| エージェントの文脈 | 呼び出しごとに再構成 | 独立エピソードから履歴を参照 |
| 次の行動の決定 | stateless Advisor が割り当て | 同質ワーカーが自律決定 |
| 中間成果の保存 | harness の状態 | アトミックコミット＋informed_by |
| 最終選択 | 測定結果を所有（規則は未確認） | 検証性能、なければ推薦多数決 |
| 主な失敗モード | 状態・要約・Advisor への依存 | 評価雑音、多数決、履歴の肥大 |

（失敗モードの行は本メモの整理であり、論文の主張ではない。）

## 4. 一致点と相違点

一致点は3つ。会話履歴を性能の源泉にしないこと、並列探索を前提とすること、中間成果を保存して後続が再利用すること。

相違点は2つ。第1は決定の集中度で、SLA は Advisor が次を決め、GitSwarm はワーカーに委ねる。第2は状態の表現で、SLA は harness が要約した証拠を渡し、GitSwarm は履歴を残してワーカーが必要なものを取りに行く。前者は文脈を小さく保てるが要約の質に依存し、後者は情報を失わないが履歴の規模に比例するコストを負う。

## 5. 多数決・共通モード障害・独立検証

**多数決の位置づけ。** GitSwarm の readout は、検証（validation）スコアが使えない場合に推薦多数決で候補を選ぶ（[2] §2.5）。検証性能で選べる実験ではこの readout を外している（[2] §3.3）。ダッシュボードにも「投票は正しさの証拠ではない（votes are not evidence of correctness）」とある（[2] §2.4）。[2] §3.5 の比較では、分散ノミネーション 62.06±2.44%（38.0分）に対し、中央セレクタ 64.40±1.49%（34.9分、+2.34ポイント）、中央アグリゲータ 58.19±4.53%（43.9分）だった。ただし9開発タスク×3シードの小規模比較で、著者ら自身が統計的同等性を示すものではないと注記している。なお、既存ノート worker02 の「検証可能な課題で多数決が有効」という整理は論文と逆である。

**共通モード障害。** GitSwarm のワーカーは同質（homogeneous）である。同質モデルが同じ誤解を共有すれば、並列化は独立した証拠を増やさない。ただし3本の論文はいずれもこれを直接測定していない。したがって「多数決が誤りを増幅する」は現時点では理論的懸念であり、実証された知見ではない。

**独立検証。** GitSwarm の Looped Transformer では、128例の評価で棄却された案を別のワーカーが512例で再評価し、改善を確認した。128例の評価は12組中5組の順位を誤ったが、512例では1組だった。評価の分解能が低いと、正しい案を誤って捨てる。DuoDiscover [3] も、代理評価器（yardstick）が真の目的から乖離し得るため、忠実性テストで順位を再検査し、ドリフトした評価器を無効化する必要を述べる。両者は「評価器そのものを検証する」方向で一致する。なお GitSwarm の活動分析でも、経験的検証はまれで、大予算でのみ目立つと報告されている（[2] §3.5）。

**示唆。** 多数決は検証不能時の決定規則に限定し、可能なら真の評価に置き換える。評価の分解能を上げ、独立検証は別モデル・別手続きで行う（同質ワーカーの再投票ではない）。

## 6. 限界と未解決事項

- 3本とも v1 の査読前プレプリント。GitSwarm は特定の商用モデル（GPT-5.5/5.6）を使い、SLA も最大10億トークン規模で、外部再現のコストが高い。
- SLA と GitSwarm のベンチマークは重ならない（SLA: SWE・カーネル・アルゴリズム、GitSwarm: 証明・ProgramBench・NN アーキテクチャ）。同一条件の直接比較は存在しない。
- GitSwarm の著者らも、ProgramBench は200問中50問の固定サブセット、IMO の全問正解は単一実行、性能への因果的寄与は未分離と明記している（[2] §4）。
- 自然言語が主体で正解が曖昧な文献調査への適用は両論文の評価対象外である。GitSwarm が検証可能な課題で多数決を外している事実は、転用に慎重であるべき材料になる。
- 本リポジトリの内部記録（文献外）：2026-10-19 の監査で、GitSwarm 模擬実験の成果物が実行値ではなく手書きだったこと、readout がコミット範囲に依存することが確認され、修正済み（`state/claims.jsonl` の CLM-004/005/007）。模擬実験のコードは `main` に含まれないため、`main` から模擬実験を再実行することはできない。

## 8. 提案（本メモでは実行していない）
