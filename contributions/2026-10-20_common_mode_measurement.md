## 2. 測定の設計

### 2.1 設定

メモ1 §8 提案2 は「**正解が既知**でモデルが苦手な課題を使い、同質ワーカーの多数決が誤りを増幅するかを**直接測る**」ことを求めている。これに忠実な設定としてjury（陪審）問題を採る。

| 要素 | 設定 |
|---|---|
| 課題 | 1,000タスク。各タスクは4候補のうち1つが正解。**正解は構成時に固定**されるため、正誤は正確に判定できる |
| ワーカー | N人（1/3/5/9/15）。全員が**同一の分布**から引かれる＝同質 |
| 読み出し | 最多得票の候補を選択。同票は最小インデックスで決定的に破棄（GitSwarm §2.5 の decentralized readout と同型） |
| ワーカー1人の挙動 | 確率 `rho` で**共有された見解** `A_t` に従う。確率 `1-rho` で独立に答え、確率 `p` で正解 |

`A_t` はタスクごとに1つだけ引かれ、それに従ったワーカーは**全員が同じ答えを出す**。これが共通モード項である。`A_t` が正しい確率を `c` とし、`c` が低いほど「共有された見解」は組織的に誤っている。

### 2.2 統制変数と操作変数

| 変数 | 意味 | 走査値 |
|---|---|---|
| `p` | ワーカー個人の精度 | 0.15 / 0.25 / 0.40 / 0.60 / 0.80（偶然水準は 1/4 = 0.25） |
| `rho` | 共有見解への追従率（＝相関の強さ） | 0.0 / 0.3 / 0.6 / 0.9 |
| `c` | 共有見解の正しさ（＝組織的バイアスの向き） | 0.0 / 0.5 / 1.0 |
| `N` | ワーカー数 | 1 / 3 / 5 / 9 / 15 |

`N` については、1タスクあたり最大15人を**一度だけ**引いて前置部分を切る。これにより N を増やすことは「ワーカーを**追加**する」ことを意味し、集団サイズの効果だけを分離できる。

### 2.3 指標

```
individual_error = 全ワーカーの回答のうち誤っていた割合（実測。1-p ではない）
plurality_error  = 読み出しが誤った選挙の割合
amplification    = plurality_error / individual_error
```

**`amplification > 1.0` は「統合したことで1人に聞くより悪くなった」を意味する。**これが CLM-003 の主張する「増幅」の操作定義である。

`individual_error` を仮定値ではなく**実測値**にしている点が重要である。追従がある場合、個人精度は `rho·c + (1-rho)·p` となり `1-p` とは一致しない。測定値どうしの比でなければ増幅率は意味を持たない。

### 2.4 事前に立てた予測

数値を見る前に、追従ブロックが読み出しを制圧する条件を解析的に求めた。

追従ブロックは `rho·N` 票を共有見解に投じる。独立なワーカーは `(1-rho)·N·p` 票を真値に投じる。共有見解が誤っているとき、ブロックが勝つのは

```
rho·N > (1-rho)·N·p   <=>   rho > p/(1+p)   =:  rho*
```

したがって **`rho` が `p/(1+p)` を超えたとき、誤った共有見解が読み出しを制圧し、増幅が起きる**。偶然水準 0.25 を超える `p` について、`rho*` は 0.40→0.286、0.60→0.375、0.80→0.444 である。この予測は §4.3 で全12セルについて検証する。

## 3. 結果

全数値は `gitswarm/artifacts/readout_sim_matrix.json`（`--check` で再実行一致を確認）。

### 3.1 発見1：ワーカーが偶然水準を下回るなら、統合は単調に悪化する

`p = 0.15`（偶然水準 0.25 未満）、`rho = 0`：

| N | individual_error | plurality_error | amplification |
|---|---|---|---|
| 1 | 0.8360 | 0.8360 | 1.0000 |
| 3 | 0.8443 | 0.8600 | 1.0186 |
| 5 | 0.8478 | 0.8790 | 1.0368 |
| 9 | 0.8423 | 0.9080 | 1.0780 |
| 15 | 0.8475 | **0.9450** | **1.1150** |

個人精度は N によらずほぼ一定（約0.845）だが、読み出しの誤りは 0.836 から 0.945 へ**単調に悪化**する。ワーカーを足すほど、間違った答えがより確実に選ばれる。これは Condorcet の逆転（anti-Condorcet）そのものであり、**「増幅」はこの領域で実際に起きる**。

### 3.2 発見2：有能なワーカーでも、誤った共有見解に従えば増幅する

`c = 0`（共有見解は常に誤り）、`N = 15`：

| p | rho | individual_error | plurality_error | amplification |
|---|---|---|---|---|
| 0.40 | 0.6 | 0.8406 | 0.9940 | **1.1825** |
| 0.60 | 0.6 | 0.7592 | 0.9640 | **1.2698** |
| 0.80 | 0.6 | 0.6821 | 0.8920 | **1.3077** |
| 0.60 | 0.3 | 0.5751 | 0.4520 | 0.7860 |
| 0.80 | 0.3 | 0.4409 | 0.1960 | 0.4445 |

`p = 0.60, rho = 0.6` の N 依存を見ると、被害が集団サイズとともに拡大することが分かる。

| N | individual_error | plurality_error | amplification |
|---|---|---|---|
| 1 | 0.7560 | 0.7560 | 1.0000 |
| 3 | 0.7693 | 0.8300 | 1.0789 |
| 5 | 0.7592 | 0.8520 | 1.1222 |
| 9 | 0.7578 | 0.9230 | 1.2180 |
| 15 | 0.7592 | 0.9640 | 1.2698 |

**個人精度は N を通じて 0.76 で一定。**変わるのは読み出しだけである。15人を集めると誤り率は 0.964 に達し、**1人に聞いた場合（0.756）より 27% 悪い**。しかも `rho = 0` なら同じワーカーが 0.020 の誤り率（amplification 0.051）なので、**同じ15人が「恩恵0.051」から「被害1.270」へ反転**している。

### 3.3 発見3：閾値 `rho* = p/(1+p)` は全12セルで的中

偶然水準を超える `p`（0.40/0.60/0.80）と全 `rho`（0.0/0.3/0.6/0.9）の12セルについて、`c = 0`、`N = 15` で増幅の発生を予測と突き合わせた。

| p | rho* | rho=0.0 | rho=0.3 | rho=0.6 | rho=0.9 |
|---|---|---|---|---|---|
| 0.40 | 0.286 | 0.499 ✗増幅なし | **1.110** ✓ | **1.183** ✓ | **1.041** ✓ |
| 0.60 | 0.375 | 0.051 ✗増幅なし | 0.786 ✗増幅なし | **1.270** ✓ | **1.063** ✓ |
| 0.80 | 0.444 | 0.005 ✗増幅なし | 0.445 ✗増幅なし | **1.308** ✓ | **1.092** ✓ |

太字は増幅（>1.0）。**12セルすべてで予測と一致**（`tests/test_readout_sim.py::CriticalRhoTest` が回帰を守る）。

### 3.4 発見4：相関だけでは増幅しない。だが統合の恩恵は完全に消える

ここが本測定の核心である。「同質ワーカー」の問題は**相関そのもの**なのか、それとも**共有見解が組織的に誤っていること**なのか。CLM-003 はこの2つを区別していない。

区別するために `c = p` とする**一致走査**を行った。このとき個人精度は

```
rho·c + (1-rho)·p = rho·p + (1-rho)·p = p
```

となり、`rho` によらず一定である。**個人の精度を固定したまま、誤りの共有度だけを動かす**統制比較になる。

`N = 15` の結果（括弧内は individual_error）：

| p | rho=0.0 | rho=0.3 | rho=0.6 | rho=0.9 |
|---|---|---|---|---|
| 0.40 | 0.543 (0.602) | 0.837 (0.609) | 0.993 (0.592) | 1.005 (0.612) |
| 0.60 | 0.067 (0.402) | 0.482 (0.392) | 0.990 (0.408) | 0.995 (0.394) |
| **0.80** | **0.000** (0.201) | **0.200** (0.206) | **0.907** (0.211) | **1.001** (0.198) |

- **増幅は起きない。**偶然水準を超える `p` では amplification は 1.005 を超えない。誤りがどれだけ共有されても、集団が1人より悪くなることはない。
- **しかし恩恵は全面的に消える。**`p = 0.80` では `rho = 0` で読み出し誤り 0.000（ほぼ完全）だったものが、`rho = 0.9` では 0.198 ＝個人誤り 0.198 と**完全に一致**する。**15人を集めても、統計的な中身は1人分である。**

これが共通モード障害の正確な姿である。誤りが「増幅」されるのではない。**N 票に膨れ上がった1つの見解が、独立な N 票のふりをする**。票の数は15倍になり、情報量は1倍のままである。

## 4. CLM-003 と HYP-002 への帰結

| 主張 | 測定前 | 測定後 |
|---|---|---|
| CLM-003「同質ワーカーの多数決は誤りを増幅させるリスクがある」 | candidate（直接証拠なし） | **条件付きで成立**。増幅は次のいずれかが必要：(a) ワーカーが偶然水準未満（§3.1）、または (b) 誤った共有見解への追従率が `rho > p/(1+p)`（§3.2）。**相関だけでは増幅しない**（§3.4） |
| HYP-002「同質ワーカーの多数決は共通モード障害に脆弱」 | testing（直接実験が不足） | **成立、ただし被害の性質が当初の想定と異なる。**被害は「誤りの増幅」ではなく「統合の恩恵の全損」である。`rho = 0.9` で N 人の読み出しは1人と統計的に等価になる |

**CLM-003 の現在の文言は不正確である。**「多数派の同意が客観的真理の代替になり得ず、誤りを増幅させる」は2つの異なる現象を1文にまとめている。測定が示したのは次である。

1. **増幅**が起きるのは、共有見解が組織的に誤っているとき（`c < p`）か、ワーカーが偶然水準未満のとき。
2. **相関のみ**の場合（`c = p`）、誤りは増幅されない。代わりに**統合の価値がゼロになる**。

2番目は1番目より厄介かもしれない。増幅なら誤り率の上昇として検出できるが、恩恵の全損は**読み出しが動いている限り正常に見える**。GitSwarm の dashboard が「votes are not evidence of correctness」（§2.4）と明記し、G.3 が票を「coordination signals, not independent proofs」と呼ぶのは、まさにこの状態への警告である。本測定はその警告を定量化した。

## 5. ResearchOS への示唆

1. **票の数を信頼指標にしてはならない。**`rho` が上がると票は増えるが情報量は増えない。`readout` を実装するなら、得票数とともに追従率（＝ワーカー間の合意度）を報告すべきである。合意度が高いほど、その票は1票分の情報しか持たない。
2. **「検証可能な課題では readout を外す」という GitSwarm の判断は、本測定でも支持される。**`rho = 0.9` の読み出しは1人と等価であり、検証スコアが使えるならそちらを使う方が strictly better である。
3. **DuoDiscover の fidelity test は `c` の継続的な監視装置として読める。**本モデルで `c` が時間とともに低下する（yardstick が drift する）なら、`rho` が `rho*` を超えた瞬間に読み出しは恩恵から被害へ反転する。§3.2 の反転は `rho` を固定しても `c` の低下だけで起きる。
4. **「同質ワーカーを増やす」は検出力を上げない。**`p = 0.60, rho = 0.6` では N=9 で読み出し誤り 0.923、N=15 で 0.964 と、**ワーカーを足すほど確実に間違う**。スケールが安全性を意味しない。

## 6. 限界（何が測れていて、何が測れていないか）

**測れていること**：正解が既知の課題において、plurality 読み出しという**規則**が、追従率・共有見解の正しさ・個人精度・集団サイズの関数としてどう振る舞うか。決定論的・再実行可能・標準ライブラリのみ。

**測れていないこと**：

1. **ワーカーは LLM エージェントではない。**`p` / `rho` / `c` は指定したパラメータであり、実測値ではない。**特に `rho`（実 LLM ワーカー群の追従率）と `c`（共有見解の正しさ）の実測値は、本メモを書いた後も依然として未測定である。**
2. **したがって「GitSwarm 型システムは誤りを増幅する」とは言えない。**言えるのは「追従率が `p/(1+p)` を超え、かつ共有見解が個人より悪いなら増幅する」という条件文だけである。その条件が実システムで満たされるかは別の測定を要する。
3. **モデルは追従を全か無かで扱う。**部分的な影響（共有見解に引き寄せられるが同一にはならない）は扱っていない。実際の同質モデルはこの中間だと考えられる。
4. **`c` と `p` はタスク間で一定。**実際はタスクの難度によって変わるはずで、難度分布によって結果は変わり得る。
5. **棄権・却下・反復ラウンドはない。**GitSwarm の Abstain（§2.3）や、DuoDiscover の真の評価による確認（§2.4）はモデルに含まない。後者が入れば `rho*` の制圧は破られる可能性が高い。**本測定は「readout 単独」の挙動である。**
6. **`p < 1/k` の領域（§3.1）は、現実のワーカーが「わざと間違える」場合にしか起きない。**偶然水準未満の精度は、報酬設計の誤りや evaluation hacking の結果としては起こり得るが、通常の状態ではない。

## 8. 提案（本メモでは実行していない）

1. **`rho` と `c` の実測。**本モデルを実ワーカー群に当てる唯一の道である。同一プロンプトから独立サンプルを N 個取り、正解既知タスクで(i)サンプル間合意率から `rho`、(ii)合意された回答の正答率から `c` を推定する。これができれば §4 の条件文は実測値に変わる。**最優先。**
2. **Abstain と真の評価の導入（§6-5）。**DuoDiscover 型の「報告前に真の評価で確認する」工程をモデルに追加し、`rho*` の制圧が破られるかを測る。
3. **`c` の時間変化（drift）の導入。**探索の進行とともに `c` が低下する設定で、恩恵から被害への反転が動的に起きるかを測る。
4. **重み付き読み出しとの比較。**票に重みを付ける方式（GitSwarm の中央セレクタ相当）が `rho > rho*` 領域で plurality を上回るか。
5. **`p` と `c` のタスク間分散の導入（§6-4）。**
