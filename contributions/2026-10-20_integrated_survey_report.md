## 1. 要旨

1. **3論文は「エージェントの会話の外に研究状態を置く」点で一致する。**対立軸は状態の有無ではなく、**状態の置き場所・次の行動の決定者・検証の接地先**の3点である。
2. **文脈を単一エピソードに詰め込む構成は、精度とコストの両方で律速になる。**全履歴保持を「選択的保持＋要約」が精度・トークン双方で上回る直接比較がある（71.0% / 1,480,996トークン → 91.6% / 553,374トークン）。「履歴は入れるほど強い」は成り立たない。
3. **検証の接地先は3種類に整理できる。**SLA は保護された評価器の測定値、GitSwarm は検証性能（検証不能時のみ推薦多数決）、DuoDiscover は真の評価 `f`（代理指標は `f` への順位相関で継続的に再検査する）。**3者とも票を検証の代替として扱っていない。**
4. **多数決は独立検証ではない。**GitSwarm 自身が票を「coordination signals, not independent proofs of correctness」と定義し、検証可能な課題では readout を剥離している。
5. **共通モード障害について、本リポジトリで決定論的測定を実施した（§5.3）。**増幅は**条件付きでしか起きない**。相関のみ（共有見解が個人と同等に正しい）場合は誤りは増幅されず、**統合の恩恵が完全に失われる**。これは従来「増幅」と一括りにされてきた現象の正確な姿である。
6. **SLA と GitSwarm の直接比較は存在しない。**ベンチマークが重ならず（SLA: FrontierSWE・カーネル・SOL／GitSwarm: 証明・ProgramBench・NNアーキテクチャ）、同一条件の比較実験はない。**優劣は決着しない。**
7. **証拠の質には大きなばらつきがある。**主要結果の大半が単一実行（n=1）、一部は固定サブセット、因果寄与は未分離。**査読済みの確定知は1件もない。**

## 3. 目的1：単一会話履歴アーキテクチャの限界

*（2026-10-20 に `contributions/2026-10-20_context_and_eval_bottlenecks.md` が処理するまで**未着手**だった項目）*

### 3.1 全履歴保持は精度・コストの両方で最善ではない

[Lodha et al., 2026] は GPT-5 に4つの文脈構成を比較させた（50タスクの経費明細化、5回の独立実行）。

| 文脈構成 | 精度 | トークン | 時間 |
|---|---|---|---|
| ユーザーモデルなし | 8.0% | — | — |
| 全会話履歴を保持 | 71.0% | 1,480,996 | 14.56時間 |
| 直近5往復に刈り込み | 79.0% | 535,274 | 5.39時間 |
| **刈り込み＋自動要約** | **91.6%** | **553,374** | 5.79時間 |

*〔証拠段階 B〕* **履歴を減らすと精度が上がり、コストが3分の1以下になる。** 制約：enterprise tool-use の1課題クラスであり、汎化は未検証。

### 3.2 文脈は分野として扱われている

[Mei et al., 2025]（1,400本超の survey）は context engineering を「情報ペイロードの体系的最適化」として定式化する。[Chen et al., 2026]（1,547本）は **long-horizon（タスク性質）／long-context（モデル性質）／long-term memory（システム性質）を峻別**し、全カテゴリ共通の発見として「horizon が伸びるほど outcome-only 指標は非情報化する」と述べる。*〔証拠段階 C〕*

### 3.3 帰属の問題

[Pilditch et al., 2026] は長期評価で観測可能性が狭まる4つの圧力を挙げ、その1つが **setup attribution uncertainty**（成績はモデルとハーネスの両方の関数）である。[Zhang et al., 2026] の Binding Constraint Thesis はさらに強い：**harness 構成がモデル選択より性能分散を支配する**（モデル固定で harness だけ変えて Terminal-Bench 2 pass@1 が 69.7%→77.0%）。*〔証拠段階 B・ただし数値は同論文が引用した外部ベンチマークの二次引用〕*

> **含意**：「文脈をどう詰めるか」と「評価値を誰に帰属させるか」は独立した問題ではない。ハーネスは文脈構築・ツール仲介・出力検証を決める層であり、その変更は評価値に直接混入する。

## 5. 目的3：共通モード障害・多数決・独立検証

### 5.1 多数決の位置づけ（文献側）

GitSwarm の readout は検証スコアが使えない場合の推薦多数決である（§2.5）。検証性能で選べる実験では readout を**外している**（§3.3）。設計比較では：

| 方式 | スコア | 時間 |
|---|---|---|
| 分散ノミネーション（plurality readout） | 62.06±2.44% | 38.0分 |
| 中央セレクタ | **64.40±1.49%**（+2.34pt） | 34.9分 |
| 中央アグリゲータ | 58.19±4.53%（−3.87pt） | 43.9分 |
| 同期ウェーブ | 63.11±0.58%（+1.05pt） | 49.3分 |

*〔証拠段階 B：§3.5, Appendix G.6 Table 13〕* **分散 readout は比較したいずれの中央集権方式にも劣後している。**著者らは9開発タスク×3シードと小規模で統計的同等性を示さないと注記しており、**分散化はスコア優位ではなくレイテンシ・構造上の理由で選ばれている**。

### 5.2 評価器そのものを検証する（DuoDiscover）

DuoDiscover の fidelity test は、安価な代理評価器（yardstick）が真の目的 `f` と同じ順位を付けるかを継続的に再検査し、ドリフトしたものを無効化する（§2.4, Appendix A.1）。**複数エージェントの合意も票も介在しない。**

- 未検証の yardstick を足すと SWE-fficiency 10.33×／SOL-Exec 66.91% となり、Claude Code の 12.85×／69.12% を**下回る**（§4, Table 4）。「評価器を置く」ことではなく「継続的に再検査する」ことが効いている。
- 検証済み yardstick のうち後に **41%（リポジトリ）／45%（カーネル）** が無効化される（§4）。ドリフトは例外ではなく常態。
- 評価の分解能が性能を変える：128例の評価は12組中5組を誤順位、512例では1組（§3.3）。

*〔証拠段階 B〕*

### 5.3 共通モード障害の測定（本リポジトリで実行した唯一の実験）

**背景**：CLM-003 と HYP-002 は 2026-10-19 の監査以来、直接証拠なしのまま据え置かれていた。メモ1 §5、メモ2 §6、GitSwarm 全文読解 §6 がいずれも「直接測定した研究は存在しない」と明記していた。

**方法**：決定論的投票モデル（`gitswarm/readout_sim.py`）。1,000タスク×4候補、正解は構成時に固定。ワーカー N 人は確率 `rho` で共有見解 `A_t` に従い、確率 `1-rho` で独立に答える（精度 `p`）。共有見解が正しい確率を `c` とする。*〔証拠段階 A：本リポジトリで再実行可能、`--check` で同一値を確認〕*

**結果**：

| # | 条件 | 結果 | 増幅率 |
|---|---|---|---|
| 1 | ワーカーが偶然水準(0.25)未満：`p=0.15, rho=0, N=15` | 個人誤り 0.848 → 読み出し誤り **0.945**（N=1 の 0.836 から単調悪化） | **1.115** |
| 2 | 有能ワーカー・追従なし：`p=0.60, rho=0, N=15` | 個人誤り 0.393 → 読み出し誤り **0.020** | 0.051 |
| 3 | 有能ワーカー＋**誤った**共有見解：`p=0.60, rho=0.6, c=0, N=15` | 個人誤り 0.759 → 読み出し誤り **0.964** | **1.270** |
| 4 | 同上 `p=0.80` | 個人誤り 0.682 → 読み出し誤り 0.892 | **1.308** |
| 5 | **相関のみ**（`c=p`、個人精度を固定）：`p=0.80, N=15` | `rho` 0.0→0.9 で増幅率 0.000→0.200→0.907→**1.001**。個人誤りは 0.198〜0.211 で一定 | **増幅なし／恩恵が全損** |

**二つの機構の分離**（本測定の核心）：

- **増幅**が起きるのは (a) ワーカーが偶然水準未満のとき、または (b) 誤った共有見解への追従率が `rho > p/(1+p)` のとき。閾値 `p/(1+p)` による予測は、偶然水準超の `p` について **12/12 セルで的中**した。
- **相関のみ**では増幅は起きない。代わりに**統合の恩恵が完全に失われる**。`rho=0.9` では15人の読み出しが1人と統計的に等価になる（増幅率 1.001）。
- すなわち共通モード障害の実体は **「誤りの増幅」ではなく「N 票に膨れ上がった1つの見解が、独立な N 票のふりをすること」** である。後者は前者より厄介である。増幅なら誤り率の上昇として検出できるが、恩恵の全損は**読み出しが動いている限り正常に見える**。

**限界（重要）**：ワーカーは指定パラメータから引いたベルヌーイ標本であり、**LLM エージェントではない**。実ワーカー群の追従率 `rho` と共有見解の正しさ `c` は**未測定のまま**である。したがって「GitSwarm 型システムは誤りを増幅する」とは言えず、言えるのは条件文のみである。詳細は `contributions/2026-10-20_common_mode_measurement.md` §6。

### 5.4 独立検証の設計

3論文を「検証の接地先」で整理すると、二項対立ではなく2軸で読む方が正確である：**何に接地するか** と **その接地をどれだけ頻繁に再確認するか**。

| | 接地先 | 再確認の頻度 |
|---|---|---|
| SLA | 保護された評価器の測定値（harness が保持） | 毎 trial |
| GitSwarm | 検証性能（検証不能時のみ推薦多数決） | 候補ごと |
| DuoDiscover | 真の評価 `f`（代理指標は順位相関で検査） | **真の評価のたびに毎回**（§2.4） |

**3者に共通するのは「同質ワーカーの再投票を独立検証とみなさない」ことである。**GitSwarm の Looped Transformer では、128例で棄却された案を**別のワーカーが512例で**再評価して復活させている。検証とは分解能を上げた別手続きであって、同じ集団の再投票ではない。*〔証拠段階 B〕*

### 5.5 評価ボトルネックの3層

検証設計を論じる前提として、**評価そのものがボトルネックになる**構造を3層に分けて押さえる（メモ2 §4 の整理を統合）。

| 層 | 何が起きるか | 根拠 |
|---|---|---|
| (a) 最終スコアが過程を隠す | 似た最終スコアの背後に異なるプロセスの詰まりがある（7モデル×36タスク）。完全評価には約10万米ドル | [9] |
| (b) 観測可能性の縮小 | within-run opacity・人手レビュー・統計的検出力・setup 帰属の4圧力 | [7] |
| (c) 誤帰属 | harness を固定してモデルだけ替えても、harness 差が 69.7%→77.0% を動かし得る | [8] |

**評価コストそのものが検出力を律速する**——真の評価1回に数時間を要する [3]。したがって「評価器を置く」ことと「その評価器を継続的に再検査する」ことは別の問題であり、§5.2 の DuoDiscover の設計は後者に直接対処している。

*〔証拠段階 B。(c) は [8] の本文確認済みの数値だが、同論文の主張は「改善」ではなく harness とモデルの**混同への警告**である点に注意。この3層の整理は論文の主張ではなく本レポートの整理である〕*

## 6. 証拠の強弱による論証

### 論証の結論

**強く言えること**（証拠段階 A または B）：

1. 会話履歴を単一エピソードに詰め込む構成は、精度とコストの両方で劣る直接比較がある（§3.1）。
2. 3論文はいずれも、研究状態をエージェントの会話の外に置く設計を採る（§4.1）。
3. 3論文はいずれも、同質ワーカーの票を独立検証の代替として扱っていない（§4.1, §5.1, §5.4）。
4. 検証不能時の多数決は、検証性能による選択が使えるなら使うべきではない（§5.1 の設計比較）。
5. 同質ワーカーの多数決について、増幅は条件付きでしか起きず、条件を満たさない場合は統合の恩恵が全損する（§5.3、証拠段階 A）。

**言えないこと**：

1. SLA と GitSwarm の**優劣**（直接比較が存在しない）。
2. **実システム**における共通モード障害の発生（`rho`・`c` が未測定）。
3. 文献調査のような**正解が曖昧なタスク**への適用可能性。両論文とも評価対象外であり、GitSwarm が検証可能な課題で readout を外している事実は、転用に慎重であるべき材料になる。
4. **因果的な主張**全般。GitSwarm の再利用も SLA の stateless 化の寄与も、因果分離はされていない。

## 8. 限界

1. **一次資料10本のうち査読済みのものはない。**すべて arXiv プレプリント（v1〜v2）である。
2. **主要結果の大半が単一実行。**SLA は Anthropic カーネル＋Codex と一部アブレーションを除き n=1。GitSwarm の IMO 全問正解も単一実行。
3. **因果は分離されていない。**GitSwarm の再利用も SLA の stateless 化の寄与も、直接的介入実験がない。
4. **本リポジトリの実験は1件のみ**（§5.3）。しかもワーカーはモデル上の標本であり実エージェントではない。
5. **`--live` による arXiv API 照合は未実施。**書誌は 2026-10-20 取得の同梱スナップショット（10件）との照合にとどまる。
6. **数値はすべて転記であり、本リポジトリでの再実験は行っていない**（§5.3 を除く）。
