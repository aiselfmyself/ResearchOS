# 並行作業の所有マップ（強制力なし）

- 作成日：2026-10-20
- 目的：複数セッションが同じブランチ群から `main` に向かうとき、**共有ファイルの同時編集**と**他人のファイルの上書き**を運用で避ける
- 強制：**なし**。CI はこの文書も `scripts/check_ownership.py` も実行しない。違反を検出・拒否・記録する仕組みは持たない
- 関連：`docs/record-id-scheme.md` §4（ID方式が解決しないと明記した項目）

---

## 1. 何を定めるか

`docs/record-id-scheme.md` §4 は「何を解決し、何を解決しないか」を表にしている。ID方式は**同一台帳への追記によるID衝突**だけを解き、次の3つを未解決として残した。

1. 同一台帳への追記による**テキスト衝突**（同じ行範囲を触る）
2. **共有ファイル**（`README.md`、`docs/`、`gitswarm/artifacts/`）の同時編集
3. **誰が変更したかの識別**（全セッションが同一 git author）

この文書は 2 を運用で避けるための所有マップである。1 と 3 は**この文書でも解決しない**（§4）。「未解決」と書かれた問題に対して、規約を足しただけで解決したとは主張しない。

## 2. 所有マップ

| パス | 書いてよい担当 | 理由 |
|---|---|---|
| `state/`（6台帳すべて。追記先は `state/<台帳名>.d/` のシャード） | **全セッション（追記のみ）** | 研究の事実データ。**2026-10-21 に統合役限定を解除した**。台帳への追記とID採番は、どのセッションも人間の承認なしに実行してよい。既存レコードの削除・書き換えは引き続き人間の承認が要る。§2.1。`state/<台帳名>.jsonl` は凍結ベースであり追記しない（2026-10-21 のシャーディング移行） |
| `README.md` | **統合役のみ**（件数の同期だけは §2.2 により全セッション可） | リポジトリの現状表明。複数セッションが同時に直すと「今どこまで進んだか」が壊れる |
| `docs/minimal-core-and-ci.md` | **統合役のみ**（件数の同期だけは §2.2 により全セッション可） | 最小コア／CIの設計記録。CIの中身と1対1で対応させる |
| `gitswarm/artifacts/` | **統合役のみ** | `benchmark.py --write` の生成物。手で書かず、統合役が再生成して入れる |
| `contributions/<自分のファイル>.md` | **各セッション（自分の1本だけ）** | 調査メモ・作業報告。1セッション1ファイルなら衝突しない |
| それ以外（`scripts/`、`tests/`、`docs/` の他文書、`task/`、`schemas/`） | **規約は何も言わない** | 下記 §5 |

補足：

- 「統合役」は役割台帳で定義された身分ではなく、**その時点で `main` への取り込みを行う1セッション**を指す。交代は人間が決める。
- 他のセッションの `contributions/` ファイルは読んでよい。**書き換えない**。
- 新しい `contributions/` ファイル名は `YYYY-MM-DD_<主題>.md`（例：`2026-10-20_ownership_map.md`）。既存の `workerNN_*.md` は改名しない。
- `state/` への追記が必要なら、**自分で書いてよい**（統合役への受け渡しは不要。§2.1）。手順は次の3つ。
  1. **追記先を作る**：`python3 scripts/new_ledger_shard.py <台帳名> --create`（例 `evidence`）。`state/<台帳名>.d/<YYYY-MM-DD>-<12桁hex>.jsonl` が作られる。**`state/<台帳名>.jsonl` には追記しない**（凍結ベース。`scripts/ledger_store.py`）。
  2. **IDを採番する**：`python3 scripts/new_id.py <PREFIX>`（`docs/record-id-scheme.md` §2）。衝突確認は統合ビュー（ベース＋全シャード）に対して行われる。
  3. **検証する**：`python3 scripts/validate_state.py` を走らせ、スキーマ・ID一意・参照整合性が緑であることを確認してから PR に出す。件数が変わったら `python3 scripts/sync_doc_counts.py` で README／`docs/minimal-core-and-ci.md` の数値行を同期する（§2.2）。
- `docs/` に新しい分析文書を足すのは可（既存の `docs/*.md` を書き換えない限り）。本マップが「統合役のみ」と名指ししたのは `README.md` と `docs/minimal-core-and-ci.md` の2本であり、その例外は §2.2 の件数同期だけである。

## 2.1 台帳への追記とID採番は全セッションが自律的に行ってよい（2026-10-21）

### 定めること

| 操作 | 人間の承認 | 根拠 |
|---|---|---|
| `state/<台帳名>.d/` のシャードへの**レコード追記**（凍結ベース `state/*.jsonl` へは追記しない） | **不要** | 取り消しが安価。CI が構造を機械的に検査する。下記 |
| **ID の採番**（`python3 scripts/new_id.py <PREFIX>`） | **不要** | 衝突しない。下記 |
| 既存レコードの**削除** | **要る** | 追記専用という前提を壊す。再現性の根拠が失われる。`docs/autonomous-merge-policy-2026-10-21.md` §1 |
| 既存レコードの**書き換え** | **要る** | 同上。訂正であっても既存行を書き換えず、新しい行を足すか `correction_note` を付けるのが本リポジトリの既存の作法（`state/sources.jsonl` の `correction_note`、`state/evidence.jsonl` の同キーを参照） |

**「追記」と「書き換え」の区別がこの規約のすべてである。** 訂正であっても既存行を書き換えない。

### なぜ安全か（2026-10-20〜21 の運用実績に基づく判断）

1. **ID が衝突しない。** `docs/record-id-scheme.md` §1 の非連番ID（`PREFIX-YYYYMMDD-xxxx`、日付＋ランダム16進4桁）は、独立したセッションが同じ日に採番しても衝突しない設計である。2026-10-20 の導入以降、**衝突は1件も起きていない**。
2. **追記の構造的な正しさは CI が機械的に検査する。** `scripts/validate_state.py`（ゲート4）がスキーマ・ID一意性・参照整合性・散文内のID/パス参照を検査する。検査対象はベースとシャードの**統合ビュー**であり、シャードにしか無いレコードも同じ規則で検証される。台帳の書誌は `scripts/check_citations.py`（ゲート5）がスナップショットと照合する。どちらもオフライン・標準ライブラリのみで再実行できる。
3. **追記は取り消しが安価である。** 履歴を追加する操作であり既存のコミットを消さない。`git revert` で1コミットとして戻せる（`docs/autonomous-merge-policy-2026-10-21.md` §3 と同じ論法）。
4. **実態として、すでに統合役を経由せずに行われており問題が起きていない。** 2026-10-21、本マップが `state/` を統合役限定としている間に、別セッションが `state/sources.jsonl` に7件・`state/evidence.jsonl` に8件を直接追記した。CI は緑のままで、ID衝突も参照不整合も生じなかった。

4 は**「規約の違反が安全だった」ことを意味しない**。**「規約のほうが実態と噛み合っていなかった」ことを意味する。** したがって規約を実態に合わせた。

### この変更が解決しないもの

| 問題 | この変更 | 状態 |
|---|---|---|
| 同一ファイルの同じ行範囲への同時追記による**テキスト衝突** | **解決（2026-10-21、方式B）**：追記先を台帳ごと・セッションごとのシャードファイルに分けた。`state/*.jsonl` と書誌スナップショットは凍結ベースになり、並行追記は別パスの追加として共存する。3ブランチ同時追記→順次マージで**衝突0**を実測（`contributions/2026-10-21_ledger_sharding_migration.md` §4）。残る共有テキストは README／`docs/minimal-core-and-ci.md` の**現在値の数値行だけ**で、`scripts/sync_doc_counts.py` が機械的に同期する（衝突しても1行） | **解決**（数値行は運用で吸収） |
| レコードの**意味的な正しさ**（EVD の excerpt が原典と一致するか等） | CI は構造だけを見る。意味は見ない | **未解決**（`docs/autonomous-merge-policy-2026-10-21.md` §5 と同じ構造。混入後の検出と訂正に賭ける設計） |
| **誰が書いたかの識別** | 何もしない。全セッションが同一 git author のまま | **未解決** |
| 追記と書き換えの**区別を機械が判定すること** | しない。`scripts/check_ownership.py` はパスの文字列しか見ないため、`state/` を触る操作が追記か書き換えかを判別できない | **未解決** |

「未解決」を「解決」と書かない。とくに1行目は、本変更によって**悪化する**方向に動いている。

### 前提の監視

本変更が安全なのは、次の2つが守られている間だけである。

- **CI が緑であること。** 緑でなければ追記をマージしない（`docs/autonomous-merge-policy-2026-10-21.md` §2 と同じ条件）。
- **追記であること。** 既存レコードの削除・書き換えが混入したら、この規約の前提が崩れている。レビューで扱う。

意味的な誤りが混入し続ける——たとえば EVD の excerpt が原典と食い違う状態が放置される——場合は、`state/` を再び統合役限定に戻すことを検討すべきである。

## 2.2 文書内の件数の同期は全セッションが自動で行ってよい（2026-10-21）

### 定めること

| 操作 | 人間の承認 | 根拠 |
|---|---|---|
| `scripts/check_doc_numbers.py` が **stale と報告した数値**の更新（テスト件数・ゲート数・台帳件数）。対象は `README.md` と `docs/minimal-core-and-ci.md` | **不要**（統合役の判断も不要。自発的に実施してよい） | 件数は再計算できる事実で、判断の余地がない。テストを足すたびに統合役の承認を待つと、件数だけが古いまま残る |

### 条件

1. **変更は報告された数値の置換に限る。** 文章の書き換えは対象外。ファイル一覧への1行追加（新しいテストファイルを載せるため）は、件数を正しくするのに必要な範囲で認める。
2. **更新後に `python3 scripts/check_doc_numbers.py` と全ゲートが緑である。**
3. **PR 本文に before / after の件数を書く。**

### 境界

- 台帳レコードの書き換え、CI 定義の変更、ゲートの判定ロジックの変更には適用しない。それぞれ従来どおり（`docs/autonomous-merge-policy-2026-10-21.md` §1）。
- 文書の散文（方針・経緯・解釈）の変更は対象外。統合役の所有のまま。
- `scripts/check_ownership.py` は**パスの文字列だけ**を見るため、`README.md` と `docs/minimal-core-and-ci.md` は引き続き `INTEGRATOR_ONLY` と分類される。件数同期はその分類に対する例外であり、分類器の判定とは別に運用する。


## 3. なぜ「強制力なし」なのか

`README.md` の凍結方針（役割分離・追記専用台帳・レビューキュー・trailer検査を含めない）に従う。同じ理由：

- 2026-10-19 の停滞は、規約を**検査で強制する**方向に進んだ結果、正常な状態を失敗として検出するゲート（`docs/minimal-core-and-ci.md` §3 の A7）を生んだ。
- パス所有の強制は、パス制限・承認・例外申請を呼び、凍結した機構の再導入になる。
- 規約は**人間とセッションが読む**ために置く。機械が赤を出すためには置かない。

したがってこのマップに違反しても CI は緑のままである。逸脱はレビュー（人間の目）で扱う。

## 4. この規約が解決しないもの

`docs/record-id-scheme.md` §4 との対応：

| 問題 | この規約 | 状態 |
|---|---|---|
| 同一台帳への追記によるID衝突 | ID方式（§1〜§3）が担当 | **解決**（既存） |
| 同一台帳への追記によるテキスト衝突 | 2026-10-21 のシャーディング移行で**解決**。§2.1 で全セッションに追記を開いたことによる発生源の増加は、追記先を分けることで吸収した（並行3ブランチで衝突0を実測） | **解決** |
| レコードの意味的な正しさ | CI は構造のみを検査する。追記を誰がしても意味は検査されない | **未解決** |
| 共有ファイルの同時編集 | 統合役1名に寄せる。ただし**強制力がない**ため、規約を知らない／忘れたセッションの編集は防げない | **運用回避のみ**（解決ではない） |
| 誰が変更したかの識別 | 何もしない。全セッションが同一 git author のまま | **未解決** |

「運用回避」は「解決」ではない。表記を混ぜない。

## 5. `scripts/check_ownership.py`（助言専用）

パスの一覧を§2の表に照らして分類するだけの小さな道具。**ゲートではない。**

```sh
# 手元で、これから触るパスを確認する
python3 scripts/check_ownership.py README.md state/claims.jsonl \
    contributions/2026-10-20_ownership_map.md \
    --session-file contributions/2026-10-20_ownership_map.md

# 差分から拾う（ローカルgitのみ。ネットワーク不要）
python3 scripts/check_ownership.py --git-diff origin/main

# 同梱fixtureで自己検証（オフライン・履歴非依存）
python3 scripts/check_ownership.py --selftest
```

分類は4種類：

| 分類 | 意味 |
|---|---|
| `INTEGRATOR_ONLY` | §2で統合役のみが触ると決めたパス |
| `ANY_SESSION_APPEND` | `state/`。§2.1により**全セッションが追記してよい**。したがって `--strict` の衝突対象から**除外**されている（2026-10-21） |
| `SESSION_CONTRIBUTION` | `contributions/` 配下。`--session-file` を渡した場合のみ「自分のファイル」 |
| `OTHER_SESSION_CONTRIBUTION` | `contributions/` 配下で、`--session-file` と一致しない |
| `UNSPECIFIED` | 規約が何も言っていない（禁止ではない） |

- 既定の終了コードは **0**（助言）。`--strict` を明示したときだけ、`INTEGRATOR_ONLY` または `OTHER_SESSION_CONTRIBUTION` が含まれれば 1 を返す。`--strict` は統合役の手元用で、CI からは呼ばない。
- `.github/workflows/core-check.yml` には**追加していない**。追加しないことが設計判断である。
- 自己検証は `tests/fixtures/ownership_cases.json`（6ケース）に対して行う。ネットワークもgit履歴も読まない。`tests/test_ownership.py` が回帰を守る。
- このスクリプトはファイルの中身・作者・コミットメッセージを見ない。**パスの文字列だけ**を見る。

## 6. やらないこと

- パス制限（write-protect）、CODEOWNERS、必須レビュー、承認台帳、例外申請フローを追加しない。
- CIへの所有検査の追加、コミットフックでの拒否、trailer での名義表明を追加しない。
- `state/` のテキスト衝突は、2026-10-21 に**方式B（凍結ベース＋セッション別シャード）**で解消した（§2 の追記手順）。1レコード1ファイル分割は採用していない（既存154レコードの移設が不要で、旧パスを残せるため）。将来、件数や要件が変われば再評価する（`contributions/2026-10-21_ledger_sharding_design.md` §3）。
- この文書を「ガバナンス文書」として拡張しない。所有の一覧と、それが解決しないことの記録以上を書かない。
