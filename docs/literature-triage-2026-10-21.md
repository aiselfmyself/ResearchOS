# 文献インベントリの粗検討（2026-10-21、アブストラクト基準）

## 0. この文書の位置づけ

ResearchOS の設計時に参照していた文献集
（`docs/literature-inventory-2026-10-19.jsonl`、54レコード）を、
**「このリポジトリ（arena.ai + GitHub による小規模 GitSwarm 型の方式）に有用そうか」**
という観点で**アブストラクト基準で粗く**選別した。

**やっていないこと**——原典の**本文**の精読、台帳（SRC/EVD）への登録。
これらは別ワーカーでの詳細調査に回す。ゆえに本稿の**優先順位**は**すべて暫定**であり、
証拠段階としては最も弱い。原典に当たらずに引用してはならない。

**判定の材料**——インベントリの各レコードが持つ `abstract_summary_ja`（日本語要約）と
`researchos_mapping`、`relevance_tier`。

> **〔2026-10-21 改訂・重要〕** 初版は「**原典の抽象にすら当たっていない**」と書いたが、
> これは**二重に不正確**だった。
> **(a) アクセスについて**：「この環境から arxiv.org には到達できない」と書いたが、
> **Arena の `fetch_page` / `web_search` では到達できる**（実測で 2 件取得できた）。
> 到達できないのはサンドボックスの `curl` / `python3` だけである。
> さらに `tests/fixtures/arxiv_metadata_snapshot.json` の `capture_method` には
> 「arxiv abs pages read via **web fetch tool**」と書いてあり、
> **このリポジトリは既に web fetch で arXiv を取得していた**。
> **(b) 原典照合について**：改訂時に優先 1・2（RRSI / Stellar Colosseum）の
> **abs ページを実際に取得し、書誌と抄録を確認した**（§6）。
> したがって「抽象にすら当たっていない」は**現在は正しくない**。
> ただし**本文は未読**であり、數値の検証もしていない。

## 2. トリアージ結果

このリポジトリの実情——**並列セッション ÷ 追記専用台帳（`state/*.jsonl`）÷ 決定論的 CI（8ゲート）÷ 統合役による裁定**——に照らした判定。

### 2.1 A：直接効く（詳細調査の価値が高い）

#### (1) `arXiv:2609.24972` RRSI: Regularized Recursive Self-Improvement of Agent Harnesses ★最優先

要約：バックボーンモデルを固定したまま、周囲のハーネス（プロンプト・制御フロー・ツール・
メモリ・コンテキスト管理）を軌跡と評価フィードバックから反復改善する。過適合を避けるため
1ラウンドの編集数を制限し、過去の採否・仮説履歴で探索の偏りを抑え、候補リーク・評価ノイズ・
性能とコストの関係をチェックし、低寄与コンポーネントを剪定する。

**なぜ最優先か**——本リポジトリは過去 2 日間で**「ハーネスが性能差の帰属先である」**
という論点（[8] arXiv:2605.23950、監査 ID 14、本リポジトリの §3.3）を繰り返し扱ってきた。
しかし**「ではハーネスをどう改善するか」の方法論を持っていない**。RRSI はそれに直接答える。

しかも RRSI の設計が**本リポジトリの既存機構とほぼ一対一で対応する**：

| RRSI の要素 | 本リポジトリの既存機構 |
|---|---|
| 差分単位でハーネス変更を評価 | PR 単位の変更 ＋ CI 8 ゲート |
| 各変更の仮説・diff・スコア／コスト差・採否を記録 | `state/verifications.jsonl`（29件）＋ `hypotheses.jsonl` |
| 失敗を次ラウンドへ再投入 | 監査の「未対応」リスト → 次の一手 |
| 固定タスクへの過適合を避ける | **未実装**（A7 の教訓はあるが、hold-out の仕組みはない） |
| 低寄与コンポーネントの剪定 | **未実装**（監査 ID 19 で「使われていない数値」は検出したが、「使われていない仕組み」は未検出） |

**A 判定の理由**：対応表の下 2 行が**そのまま本リポジトリの未実装項目**として読める。

#### (2) `arXiv:2609.15983` Stellar Colosseum: A Many-Agent Harness for Long-Horizon Research

要約：証明構築の前に戦略を並行探索し、経路が分解可能な成熟度に達したかを gate で判定する。
節単位の依存関係を持つサブ問題を作り、Verifier の指摘を**影響箇所へ戻し**、候補と批判を統合する。

**「反証を局所箇所へ返す修復ループ」**が本リポジトリの `counterclaim_ids`（監査 ID 5）と
同じ発想である。ただし本リポジトリの台帳は**反証を記録するだけで、影響箇所への返し方を持たない**
——`VER` は `target_id` を 1 つ持つが、「この反証は CLM-003 のどの部分を崩すか」までは表現していない。
**台帳スキーマを拡張する際の具體的な設計例として価値が高い。**

### 2.2 B：条件付きで有用

#### (3) `arXiv:2610.18933` The Agentic Scientist

草案化→アイデア生成→計画→サンドボックス実験→結果統合→ベースライン/アブレーション→
事後分析→報告、を並列コーディングエージェントと段階別ルーブリック検証で接続する。

本リポジトリは**すでに非形式に同じこと**をしている（並列セッション ÷ 統合役 ÷ CI）。
したがって「新しい設計」としては小さいが、**段階別ルーブリック**の具體例は
「長文生成の機械検査」（監査 ID 11、検査7）を**段階ごとに設計する**際の参考になる。

#### (4) `arXiv:2610.18025` SHELDON: Dual Search over Hypothesis and Observation Spaces

仮説空間と観測空間を別々に表現して同時探索し、**仮説が説明できない観測**から理解の欠落を検出する。

本リポジトリの `hypotheses.jsonl`（2件）は**仮説しか持っておらず、観測との対応がない**。
ID 17（`rho`/`c`）は凍結されたが、凍結理由は「非定量的テーマでは難問」であって
「仮説管理が不要」ではない。**台帳を拡張するなら**この分離は有力な設計指針になる。

#### (5) `arXiv:2602.13830` A Tale of Two Graphs

知っている意味的知識と、報告書のアウトラインを**別々のグラフ**として管理し、
両者の構造を照合して欠けた関係を発見し、次の検索クエリを生成する。

本リポジトリの規模（メモ17件・EVD 49件）では**グラフ構造を持ち込むほどではない**と判断。
ただし「統合レポートのアウトライン」と「台帳の中身」の**食い違いを機械的に検出する**という
発想は、監査 ID 19（文書内の数値ドリフト検査）の一般化として面白い。**規模が 3〜5 倍になったら再検討。**

#### (6) `arXiv:2609.37633` RLTL;DR

失敗後に Verifier が出した評価を、モデル自身が短い insight へ圧縮し次の rollout へ渡す。

本リポジトリの `VER.rationale` は**長文で、再利用されていない**。
「検証結果を短い知見に圧縮して次に渡す」は**統合役の作業を軽くする**方向性として筋が良い。
ただし本リポジトリは LLM の学習を行わないため、"internalize" 部分は採用できない。

## 3. ID 18（「ハーネスは順位を変えるか」の検証）との関係——正直な評価

**ID 18 が必要とするもの**＝「**同一タスク領域内で、モデルの広がりを変えた**第3の論文」。
すなわち `R =（モデル間の広がり）/（ハーネス間の広がり）` の閾値 ~1 を検証するには、
タスクを固定したまま**モデル格差だけを変えた**実験が要る。

**今回の候補でそれを満たすものはない。**

- **RRSI** は逆で、**モデルを固定してハーネスを変える**。これは ID 18 の検証そのものではないが、
  **「ハーネス側の広がり」を系統的に作り出す方法**としては使える可能性がある。
- **Stellar Colosseum** は「並列候補」を持つが、格差を変えた比較の報告ではない（要約からは読み取れない）。
- 他はタスク領域も対象も違う。

**結論**：ID 18 は**このインベントリからは解決しない**。別の探索（SWE-bench 系の
マルチモデル比較でモデル格差を明示している論文）が必要である。
ただし **RRSI は ID 18 とは独立に、本リポジトリへの有用性が最も高い**ため、
ID 18 の成否にかかわらず詳細調査に回す価値がある。

**特に 3 番目は重要**——本稿が RRSI を最優先としたのは**要約の内容**に基づくのであって、

## 6. 〔2026-10-21 改訂〕原典で確認できたこと

人間の指摘でアクセスを再確認したところ **Arena の `fetch_page` で arxiv.org に到達できた**ため、
**優先 1・2 の abs ページを実際に取得して書誌と抄録を確認した**。

### 6.1 RRSI（`arXiv:2609.24972`）——抄録で確認

- 現在版は **v3**（2026-10-04）。**インベントリは `v2` と記録しており 1 世代古い**
- 著者 14 名（Peng Xia … Tomas Pfister, Chen-Yu Lee）。cs.LG / cs.AI / cs.CL
- 抄録で**當方の設計と食い違う點**が判明した——これが本改訂で最も重要な収穫である：

| 當方の暫定実装 | RRSI の実際の機構 | 差分 |
|---|---|---|
| `holdout_eval.py`（dev/hold-out 分割で過適合を検出） | **critic** が **benchmark-specific な提案を篩にかける** | 目的は近いが、**critic は提案の採否段階で働く**のに対し、當方は「検出器が一般化するか」を見ている。**別物の可能性が高い** |
| `prune_candidates.py`（`has_tests` / `referenced_in_docs` / `imported_by` で判定） | **pruner** は「**too small / too expensive / no longer useful**」を剪定する | **基準が違う**。當方は「使われているか」の代理指標、原典は「**寄与の大きさ・コスト・陳腐化**」 |
| （「1 ラウンドの編集数制限」は PR レビューが担うとして実装しなかった） | **proposer の temporally annealed budget** が編集の束ね数を制限する | **原典に實在する機構**を當方は意図的に外していた。再考の余地がある |

- **コストが成果に含まれる**：「30% fewer policy tokens than the unregularized evolution」。
  つまり**剪定は性能だけでなくコストでも判定される**——當方の実装はコストを全く見ていない。
- **コードが公開されている**：`https://github.com/google-research/rrsi`。
  `github.com` は**サンドボックスの curl からも到達可能**なため、
  **本文が読めなくても実装を確認できる経路がある**。

**結論**：當方の暫定実装 2 本は**方向としては妥当だが、原典の基準とは異なる**。
どちらも**抄録要約だけを根拠に設計した**ものであり、原典を読めば設計が変わりうる。
詳細調査（別ワーカー）では**実装の擁護ではなく、原典に照らした判定**を求めている
（`docs/worker-handoff-literature-2026-10-21.md` の優先 1）。
