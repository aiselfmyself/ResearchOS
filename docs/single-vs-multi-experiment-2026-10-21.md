## 1. 研究問い

> **同一の項目抽出タスク集合（ §5 の51項目）について、3分割＋統合は単独遂行と比べて壁時計を短縮するか。また総セッション時間（コストの代理）と項目誤り率はどう変わるか。**

副次的には、分割したときに統合へ回る手直し（形式不整合・マージ競合・人間の追加介入）がどれだけ発生するかを記録する。これは主要評価指標 M4（ §9）として測るが、判定規則（ §11）の主軸は壁時計・誤り・総時間の3点である。

「複数ワーカーは動く」ことは前回実験 E1 で確認済みである。欠けているのは「単一より得か」の同条件比較であり、本実験はそこだけを測る。

本リポジトリの実際の作業型のうち「**論文一次資料からの項目抽出**」を選ぶ（前回 A / A' が行った型であり、読解ワーカーの通常作業でもある）。既存メモ claim の原典照合型も候補だったが、照合型は対象メモ自体がリポジトリ内にあって両アームが同じ中間生成物を見る分だけ条件が複雑になるため、初回の同条件比較としては抽出型を採る。判定規則が指す「運用の既定」も、まずは抽出・照合のうち抽出型について述べる（ §11）。

### 2.3 設計者の既見範囲の開示

項目を実在の節・表に固定するため、設計者は abs ページと HTML v2 の**骨格**（節見出し、表・図のキャプション、表の行・列見出し、列挙の所在）を確認した。出題者と受験者は別の存在である、という通常の試験設計と同じ構えであり、以下を規約とする。

- **本書に答え（項目の値そのもの）は一切記録しない。** 本書の例示数字はダミーである（ §4 の書式例など）。項目表（ §5）は問い・型・所在ヒントのみから成る。
- 設計の担当は X3 のいずれのアーム（単一・P1〜P3）も務めない。
- 真値は別セッションの X4 が、全出力の固定後に原典からのみ確定する（ §8）。設計者の記憶を真値の経路に入れない。
- 骨格既見による項目選択の偏り（例：見つけやすい項目ばかり選んだ可能性）は、両アームに共通に効くため内部比較は保たれるが、結果を他のタスクへ外挿する際の制限になる（ §12）。

### 2.4 リポジトリ内要約による汚染の扱い

インベントリには本論文の v1 時点の書誌と日本語要約がある。したがって書誌系の項目（ §5 の A 層の一部）は、本文を読まずにリポジトリ内要約から近似できてしまう項目を含む。これを隠さず、次のように扱う。

- A 層は、版固定の確認を兼ねる項目（固定版の改訂日、所属、分類コード等、インベントリ要約に無い情報）を中心にし、要約から写せる書誌項目の数は絞ってある。
- 両アームへの指示：回答の根拠は**固定版の一次資料のみ**とし、各項目の `location` には一次資料内の所在を書く。所在が一次資料でない項目は、X4 が「手順逸脱」として数えて記録する（採点自体は値で行うが、逸脱件数は副次指標として報告される）。

## 3. 前回実験の経緯と教訓への対応

前回（E2）は15項目で実施し、単一の正解を定められたのは**8件**に留まった。その8件で両セッションとも**誤り0件**だったため、誤りに関する観測そのものが得られなかった（結果メモ §2.3〜§2.4。計測器も「n_joint=8 < 30」と警告した）。表面の不一致6件のうち事実の食い違いは0件で、書式差・自由選択の取り違え・項目定義の不備に分解された（同 §2.2）。

本実験の項目設計は、この経緯への応答として次の対応を取る。右列は本書の該当箇所である。

| 前回の教訓（出所） | 本設計での対応 |
|---|---|
| 自由記述・自由選択の項目は、両者が正しくても食い違う（結果メモ §3-1、凍結 §6.3-1） | 項目は**指定式**のみにする。表なら行ラベル×列ラベルでセルを一意に指す。本文数値なら節と文脈で対象を一意に指す。「代表値を挙げよ」型は置かない（ §5） |
| 「いくつあるか」は数え方を定義しないと測れない（同 §3-2、凍結 §6.3-2） | 数える項目にはすべて**数え方の規則**を項目表と §4 に明記する（何を1件と数え、何を数えないか） |
| 値の比較は文字列ではなく意味で行う（同 §3-3、凍結 §6.3-3） | 回答の型を数値・列挙・短文逐語・日付に制限し、単位換算と正規化の規則を事前に定める（ §4）。採点道具（X2）には `scripts/measure_agreement.py` の比較流儀（数値許容誤差、空白圧縮と大小無視、列挙は順序無視、`null`/`"unknown"` は棄権）の踏襲を要求する（ §9） |
| 素の一致率は過小評価になるため不一致の内訳を必ず併記する（同 §3-4、凍結 §6.3-4） | 採点分類として「正解／事実誤り／書式差のみ／棄権／欠落／項目側の問題（除外）」を事前に定め、誤り率は事実誤りのみを数える。分類基準は §9 に列挙する |
| 正解可能8件は少なすぎ、誤りが観測できなかった（同 §2.4） | 項目総数を **51件**にする（ §5）。真値確定項目が8割残れば約40件となり、誤り率が数％程度の作業でも誤りの有無が観測できる規模を狙う。それでも両アーム誤り0件はあり得るため、その場合の判定の分岐を事前に書く（ §11） |
| 対象文献の版を固定してから配る（凍結 §6.3 追加分） | 固定版 v2 と版付き URL のみを使い、開始時に版表記の転記・照合を求める（ §2.2） |
| 計測器の流儀：棄権（`null` / `"unknown"`）は正解でも誤りでもない（measure_agreement docstring） | 見つからない項目は推測で埋めず `value: null` とすることを両アームの規約にする。棄権の分母への入れ方は §9 で事前に固定する |

## 4. 項目の共通規則

### 4.1 回答の型（この4種以外は使わない）

| 型 | 意味 | 書式の規則 |
|---|---|---|
| 数値 | 整数または小数 | JSON の数値型で出す（文字列でごまかさない）。原典で「99.9%」のように % が付く値は、**数値部分のみ**を出す（99.9 の部分。例はダミー）。範囲は下限・上限を別項目に分けてある。近似記号（≈、∼）が付く値は数値部分のみを出す（該当項目に明記） |
| 列挙 | 原典が列挙する名称・値の一覧 | JSON リスト。要素は原典表記のまま。順序は原文順を推奨するが、採点は**順序を無視**する（多重集合として比較）。原典自身が要素数（「three baselines」等）を明示する項目では、その個数も問いに含める——完全性の自己点検のためで、要素自体は与えていない |
| 短文逐語 | 原典の短文・名称の原文まま引用 | 引用符は付けず文そのものを出す。長い要約や言い換えは対象にしない。対象は原典で引用符付きで提示される例文、表の中の短文、固有の名称表記に限る |
| 日付 | 書誌日付 | `YYYY-MM-DD` 形式の文字列 |

- 単位換算が要る項目は **Q33 のみ**である。規則：原典表記 `k` は ×1,000、`M` は ×1,000,000 として**整数に換算して**出す（例「3k」→ 3000。例はダミー）。真値も同じ換算を行い、整数同士で比較する。
- **数える項目の共通規則**：数える対象は各項目に明記し、重複参照（本文中での再言及）は数えない。表・図の数はキャプション「Table N:」「Figure N:」を持つ実体のみを数え、本文中の参照言及は数えない。判断対象は固定版 HTML に表示される構成である。
- **図の目視読み取りは出題しない。** プロット曲線から読み取る値は一意でないためである。図に関する項目は、キャプション文中に明記された数値と、図そのものの数（ §4 の数え方）に限る。
- `location`（出力側）は各項目とも一次資料内の所在（節番号・表番号・キャプション等）を自由書式で書く。見つからなければ `value: null`、`location: null`、`confidence: "low"` とし、実施メモに「探した範囲」を書く。推測で値を埋めない。
- `confidence` は `high` / `medium` / `low` の自己申告とし、主要指標には使わない（内訳観察用）。

### 4.2 取得経路の統一

- 両アームとも HTML 版（ §2.2 の版付き URL）を Arena の web fetch で取得することを既定とし、PDF を使う場合はその旨をメモとセッションログに残す。HTML の表レンダリングには数値表記の癖がありうるが、それは両アーム共通の測定条件である。表記が確定できなければ真値確定段階 (§8) の除外規則（ §8）で処理し、片アームだけ損にしない。

## 6. 配分（3つの部分集合）

- 並行アームは P1 / P2 / P3 の3ワーカーとし、各 **17 項目**を担う。割当は §5 の「担当」列で固定する。
- 配分方針は **節（所在層 A〜D）と型（数値／列挙／逐語・日付）による層化** である。各部分集合が各層・各型から似た数を受け取るよう割り付けた。内訳は次のとおり（本書の作成時に項目表から数え直して一致を検証した。検証の位置付けは §14）。

| 部分集合 | 件数 | A層 | B層 | C層 | D層 | 数値 | 列挙 | 逐語・日付 |
|---|---|---|---|---|---|---|---|---|
| P1 | 17 | 3 | 4 | 5 | 5 | 12 | 3 | 2 |
| P2 | 17 | 3 | 4 | 5 | 5 | 11 | 3 | 3 |
| P3 | 17 | 4 | 4 | 5 | 4 | 11 | 3 | 3 |

- 節ごとに塊で分ける案（例：P3 は付録だけ）は採らない。付録探査のような層固有の難易度が「ワーカーの差」と交絡し、アーム間比較の前に部分集合間の難易度差が結果を支配しかねないためである。
- 代償として、各 P ワーカーも原典全体を航行する必要がある（17項目が全文に散る）。したがって本実験の並行条件は「読む範囲そのものを分割する運用」より速くならない形の分割であり、壁時計の利得は過小側に出うる。この当たりは限界に明記する（ §12）。均等な担当件数と難易度の層化を優先する人為は、運用実験として保守的である代わりに、何が短縮に効いたかの切り分け（分担そのものか、担当範囲の狭さか）は問い分けない。
- 単一アームは §5 の **全51項目**を1ワーカーが実施する。両アームの項目集合は完全に同一であり、並行アームの和集合 = 単一アームの集合である。

## 7. アーム定義・同条件性・実行順序

### 7.1 アームと成果物の場所

成果物のファイル名は割当文書の X3 プロンプト案に従い、本書で固定する（実ファイル名の日付部は実行日が入る。contributions 配下のみとし、`state/` やコードは変更しない）。

| アーム | ワーカー表記 | 担当項目 | 成果物（新規作成のみ） |
|---|---|---|---|
| 単一 | `S` | 全51項目 | `contributions/《YYYY-MM-DD》_svm_single.json` と `.md` |
| 並行 | `P1` / `P2` / `P3` | 各17項目（ §5 の担当列） | `contributions/《YYYY-MM-DD》_svm_parallel_p1.json` 等と各 `.md` |

出力 JSON の外側形は全ワーカー共通とする。

```json
{
  "arm": "single または parallel",
  "worker": "S または P1 / P2 / P3",
  "base_commit": "開始時点で記録した共通分岐元コミット（短縮可）",
  "items": [
    {"id": "Q01", "value": "《型どおりの値、または null》", "location": "《所在、または null》", "confidence": "high | medium | low"}
  ],
  "session_log": "§10 の仕様"
}
```

並行アームのワーカーは担当外の項目を `items` に含めない（分母が壊れるため）。単一アームは全51件の行を持つこと（見つからない項目も棄権として行を持つ）。

### 7.2 同条件性

| 要素 | 規則 |
|---|---|
| 分岐元 | 両アームの全セッションは**同一の base コミットから開始**する。実務として、人間が投入直前に `main` の HEAD を控え、4セッションをその状態で立て、各ワーカーは開始時の HEAD を `base_commit` に記録する。X4 は4件が一致するかを照合し、不一致は実験運営の失敗として記録する（ §12） |

| プロンプト | 投入文は割当文書の X3-S / X3-P テンプレートを土台とし、アーム間で文面をそろえる（担当範囲とファイル名のみが差分）。実際に投入した文面を人間が保存し、X4 の結果資料から参照できるようにする |

### 7.3 汚染を防ぐ実行順序（固定）

1. **D2 で本書の内容を確定**（項目表・配分・指標・判定規則の数値を人間が承認し、承認値を記録する）。
2. X2 が採点道具を本書の §9・§10 の仕様に合わせて実装し、`main` に着地させる（割当文書の手順どおり）。
3. 人間が4セッション（S、P1〜P3）を立てる。**各セッションは実行中、他アーム／他ワーカーのブランチ・PR・成果物を見ない**（PR 一覧を他条件の調査に使わない、他ワーカーのファイルを引かない）。自分のブランチと base 時点の `main` だけを見る。
4. 各ワーカーは PR を作成し、CI が緑ならマージしてよい（出力を固定する行為が手順の一部であるため。割当文書どおり）。**全4セッションの出力が PR として固定された時点で「出力固定完了」**とする。固定以後の修正コミットは測定を壊すため行わない。
5. **真値の作成は、出力固定完了のあとにだけ**始める（ §8）。固定完了までの期間は、誰も「正解表」をリポジトリ内に作らない。
6. X4 が真値確定と採点・結果統合を行う（固定された全出力が揃っていなければ開始しない）。

順序を崩した場合の扱い——手順逸脱が起きたセッションがある場合、X4 は逸脱の内容と該当ワーカーを明記し、結果の格（判定規則まで進めるか、逸脱により無効として参考報告に留めるか）を人間の判断に上げる。逸脱を無かったことにして定量する、はしない。

## 8. 真値手順

担当：**統合役（X4 ワーカー）**。実施時点： §7.3 の出力固定完了の後。

1. **盲検的真値作成**：X4 は真値 JSON を完成させてコミットするまでは、アーム出力の JSON を開かない（ファイルの存在・PR の着地確認は可）。真値は固定版一次資料のみから、項目ごとに「値＋出典位置（節／表／キャプション等）＋照合用の短い原典抜粋」で確定する。

   注：割当文書の X4 プロンプト案は「アーム出力の内容を参照してよい」と書くが、本書は盲検側に倒して事前に固定する。D2 で確定させる前提として相違点を明示する。

2. **真値 JSON の形式**（成果物は割当文書どおり `contributions/《YYYY-MM-DD》_svm_truth.json`）

   - `source`：固定版 URL と版
   - `base_commit`： §7.2 の共通分岐元
   - `items[]`：`id`、`value`（ §4. の型どおり。Q33 は換算済み整数）、`location`、`evidence_excerpt`（抜粋）
   - `excluded[]`：`id`、`category`（下記（a）／（b）／（c））、`reason`

3. **真値が定まらない項目の扱い**：次の場合は値を無理に置かず、**両アーム共通に真値不確定として分母から除外**し、理由を `excluded` に記録する。

   - （a）原典に該当する情報がない、または所在が特定できない
   - （b）原典の内部で表記が一意でなく、 §4. の指定でもなお複数の正当な答えが残る
   - （c）取得経路上のレンダリングでは数値・表記が確定できない

4. **除外が多い場合の格判定（提案として事前明示）**：除外が全51項目の2割を超える場合は「項目設計の相当部分が機能しなかった」ものとして扱い、誤り率による判定は行わず、設計失敗として報告する（判定規則の分岐として §11 に入れる）。ただしこの割合の閾値は D2 で人間が確定する。

5. **人間によるスポットチェック（提案）**：確定した真値について、人間が無作為数項目（目安5件）だけ原典と照らし、相違があれば当該項目を除外側に回す。実施したか否かと件数を X4 レポートに記録する。スポットチェック手段を持たない（時間が無い）場合は未実施として格を明記する。

6. X2 の集計結果に対する全不一致の目視分類（事実誤り／書式差／欠落／棄権／項目側の問題）は次節の分類規則に従い、X4 が行う。前回体験どおり、機械判定の生の不一致をそのまま誤りにしない。

## 9. 主要評価指標（4つ以内に事前固定）

主要指標は次の**4つ**とし、判定規則（ §11）はこの4つのみを根拠にする。それ以外の数値はすべて「副次指標」に分類し、解釈の補助として併記はするが、判定の根拠には使わないとここで宣言する。

| 番号 | 指標 | 操作的定義 | 測る主体 |
|---|---|---|---|
| M1 | 壁時計（アーム別） | そのアームの**最初のプロンプト投入の時刻から、そのアームの全 PR がマージされた時刻**まで。単一アームは1プロンプト→1PR。並行アームは3プロンプトのうち最初の投入時刻→3 PR のうち最後のマージ時刻（投入の時間的ばらつきも並行アーム側に含む保守的な定義とする。投入時刻3点自体も併せて残し、投入ラグの内訳をあとで分離できるようにする） | 人間が記録（付属表 §13.2）。PR 時刻は GitHub で裏付け得る |
| M2 | セッション総時間の合計（アーム別） | セッションログの `started_at_utc` から `finished_at_utc` までの経過時間をワーカーごとに求めた**合計**。単一は1セッション分、並行は3セッションの和。`started_at_utc` は作業開始直後にシェルで確認した時刻であり、それより前のプロンプト読解時間は含まれない（全ワーカー共通の測定外として明記する） | 各ワーカーのセッションログから X4 が集計 |
| M3 | 項目誤り率（アーム別） | `事実誤りの件数 ÷ 真値確定項目の件数`。分母は §8 の除外を引いた真値確定項目とする。単一アームは全真値項目が分母、並行アームは割当どおり合計して分母とする。棄権・欠落は分子に入れないが分母には入れる（棄権によって誤り率が見かけ上良化することを防ぐため。未回答の程度そのものは、下記の副次指標で併せて見る） | X2 道具で機械分類した後、X4 が全不一致を目視で分類 |
| M4 | 統合オーバーヘッド（アーム差として） | 両アーム共通の真値・採点作業を**除き**、アームの形が原因で生じた余分な作業を次で数える：(i) PR のマージ競合の件数、(ii) X2 道具がそのまま読めず統合側の手直しが要った項目・ファイルの件数（JSON 形状、ID 不整合、担当外漏れ等）、(iii) 投入以外に人間が介入を迫られた回数（催促・指示の追記・復旧相談など）。回数と内訳を列挙する | X4 と人間が事象ベースで記録（PR の状態・人間の介入ログを材料にする） |

### 採点分類の定義（M3 の分類語彙）

- **正解**：原典の情報として正しい値で、 §4. の型として真値と一致する（X2 の正規化比較の範囲）。
- **事実誤り**：原典に照らして事実として異なる値。数値の取り違え、別行・別セルの値、真値集合以外の要素を出した列挙、逐語文の言葉の置き換えなど。
- **書式差のみ**：情報としては真値と同一で、相違が表現上のものに限る。具体的には空白・行内空白の多少、大文字小文字、語末句読点の有無、% 記号の残存、数値字面の小数表記差（同一値に評価されるもの）、列挙順序の差、該当項目における慣用的な表記ゆれを真値が許容 variant として定義したもの。**書式差のみは事実誤りに数えない**。正解と同列に分子から外し、件数は別枠で報告する。
- **棄権**：`value = null`。`"unknown"` という文字列で提出された場合は棄権として扱うが、本来の形式からの手直しとして M4(ii) にも記録する。
- **欠落**：担当項目に `items` の行自体がない。
- **項目側の問題**： §8 で除外された項目（真値不確定）。両アーム共通に分母から除く。

M3 には固有の感度問題があるため、次を副次表示として**必ず併記**する：未回答率 `（棄権＋欠落）÷真値確定項目`、書式差の件数、「回答した真値項目に限った事実誤り率」（棄権を分母からも外した場合の率）、アーム間の不一致内訳の全件表。

## 10. コスト記録の形式（セッションログ JSON 仕様）

各ワーカーの出力 JSON にある `session_log` は次を必須とし、未取得の項目は `null` と理由を `notes` に置く（黙って欠落させない）。時刻書式は UTC の ISO 8601 とする。X2 は当該形を入力契約として扱う。

| 欄 | 型 | 必須 | 定義 |
|---|---|---|---|
| `arm` | 識別子 | 必須 | `"single"` または `"parallel"` |
| `worker` | 識別子 | 必須 | `"S"` または `"P1"/"P2"/"P3"` |
| `branch` | 文字列 | 必須 | 作業したブランチ名 |
| `base_commit` | 文字列 | 必須 | §7.2 の共通分岐元コミット（自身が開始時に見た HEAD） |
| `started_at_utc` | 時刻 | 必須 | 作業開始の最初の行動として `date -u +%Y-%m-%dT%H:%M:%SZ` で取った時刻 |
| `finished_at_utc` | 時刻 | 必須 | 成果物 JSON の内容を確定した時刻。この範囲に、その後のゲート実行・PR 作成の時間は含まれない。その分は M2 ではなく壁時計 M1 側の時間として現れる |
| `tool_calls` | 整数、または `{"total": 整数, "by_kind": {種類名: 整数}}` | 必須（少なくとも総数） | 下記の数え方規則 |
| `files_read` | 文字列のリスト（重複なし） | 必須 | 読んだものの一覧。リポジトリ内は `docs/` 等からの相対パス、一次資料は取得した URL（**版付き**）。同一源を複数チャンクで読む場合も、源 URL は1件として記し、可能な場合に取得回数の注記を `notes` に残す。読み直しの有無は、複数チャンクの回数程度の粒度でよい |
| `output_files` | リスト | 必須 | 作成した成果物ファイル名（JSON とメモの両方） |
| `notes` | 文字列 | 任意（空欄可） | 中断・手順逸脱・固定版の版表記の転記・UI 上モデル名（あれば。なければ unknown）・困った点。短く自由に書く |

### `tool_calls` の数え方規則（全ワーカー共通）

- 数える対象は、セッションが発出したツール呼び出しである。`bash` の1回実行を1とする。シェル内でのパイプ・複合コマンドで重ね数えをしない。ファイルを読む・取得する・書く・編集するツールも各1回を1として数え、 `git`／`gh` を `bash` 経由で使った場合はその `bash` 1回としてのみ数える（二重に数えない）。
- 並行発出した呼び出しは、発出した1個ずつを数える（まとめて1にしない）。
- 種類別内訳（`bash`／ページ取得／ファイル読取／ファイル書込・編集／その他）が記録し直せる範囲で分かれば `by_kind` を強く推奨する。総数は内訳の合計に一致させる。
- この数え方は自己申告に基づく概数であり、後から厳密に再構成することは求めない。途中で数え落としに気づいた場合は、その旨を `notes` に残す。自己申告値であることは、副次指標の解釈に必ず明記する。

## 11. 判定規則（数値は提案、D2 で確定）

以下の閾値・差の許容範囲は**すべて提案値**である。人間は D2 にてこの表の数値を議論して確定し、確定値を X4 の結果メモ／D2 の記録として結果を見る前に残す。結果が出た後に閾値を動かす場合は、新たな人間判断として日付と理由を記録し、もとの事前登録提示値との差分を宣言する（事後改定を事前登録に見せかける行為はしない）。

| 区分 | 規則の提案 |
|---|---|
| 3分割を既定にする条件（下記をいずれも満たす場合） | (i) M1：並行の壁時計が単一の **0.70 倍以下**（30%以上短い）。(ii) M3：事実誤りの件数が単一に比べて**+2件以内**である（悪化がその範囲）こと。かつ、未回答（棄権＋欠落）の件数差も **+2件以内**であること。(iii) M2：並行の総セッション時間が単一の **1.5倍以内**であること。(iv) M4：形式手直しが小幅に留まっていること（提案：手直し件数が真値確定項目数の1割未満であり、出力全体が機械処理できないような構造的な崩壊がないこと） |
| 上記を満たした場合の運用への反映 | 「抽出・照合型タスクの既定は3分割」を採用する。反映先はプレイブック改定 PR とし、人間の承認を経る。反映範囲は本種の抽出型タスクのみとし、自由作文型タスクの既定は変更しない |
| 一部条件のみを満たす場合 | 期限が明確に重要な条件付きタスクでの限定的採用として人間が個別に判断するに留め、常時の既定にはしない。特に M2 や M4 が上限を超過した場合は、速度の利得を統合と読み直しのコストが相殺しうるためである |
| 誤り条件を満たさない場合 | 単一を既定として維持する。P 並行のうち誤りが集中した局面（層・種類）は今後の分割設計で担当させない等のガイドラインの材料にする |
| 判定不能の分岐 | §8 の除外が上限として定めた割合を超えた場合、または両アームとも事実誤り0件で M3 の悪化有無が判別不能だった場合は、「誤り率は比較材料が得られなかった」ことを明示し、抽出型の既定変更は時間条件のみで自動に決定しない。分割を試行導入するか・もっと難しい項目束で再実験するかは人間が選ぶ |

差を「+2件以内」のような件数で書くのは、真値確定項目が最大で51件しかなく、比率で精密に書くほどの分母ではないからである。差が2件を超えた場合でも、統計的根拠をもって「悪化した」と断言するものではなく、生件数と内訳の表を前に人間が運用判断を行う（判定規則の数値は、その判断の目安を事前に宣言したものである）。

## 12. 限界

- **試行回数**：各アームは1回きりのパイロットである。統計的検定はしない。件数と内訳で述べるのみである（前回の結果メモ §2.4 でも警告された論点）。観測された差が小さい場合、それが「アームの違いによる効果」なのか「当たったワーカー個体の違い・投入した時間帯の違い」なのかを分離することはできない。
- **モデルの同一性**： §7.2 のとおり、Arena 上では各セッションの基盤モデルを統制できず、同一であることも異なることも確認できない。アーム間差にはモデル差が交絡しうる。本実験の結果は「この環境での運用の観察」であって、特定モデルについての主張にはならない。
- **人間の直列ボトルネック**：4セッションの開始指示、プロンプト投入、PR の確認は人間の直列作業であり、壁時計 M1 にそのまま混入する。特に並行アームは投入が3回ある分だけ構造的に不利な定義（ §9）である。投入時刻をワーカーごとに残すのは、この内訳を事後に分けて読むためである。投入者（人間）の作業速度そのものは測定対象ではない。
- **対象の狭さ**：対象は1本の論文からの抽出型タスクだけである。既存メモの原典照合型、長文の作文型、コード実装型へ結果を一般化はできない。項目も表セルと本文明記数値が中心であり、「読んで要点を掴む」種類の作業の分割可否はこの実験の外にある。
- **配分の人為性**：層化のために各 P ワーカーの担当は全文に散っており、各ワーカーも全文を航行する。実務でよくある「節ごとに範囲を分ける」運用なら、並行アームの読み量はもっと減り、壁時計はさらに短くなりうる。本実験が測るのはその運用形態ではなく、難易度をそろえたうえでの分担そのものの効果の側である。範囲分割との違いは結果の解釈材料として、X4 の報告で区別して述べなければならない。
- **項目選択の偏り**：設計者は骨格を見て項目を選んだ（ §2.3）。見つけやすい値に寄った選択なら両アームとも誤りは出にくく、誤り率差は観測されにくい。両アームへの効き方は共通なので内部比較は壊れないが、「業務の項目一般」への外挿の根拠にはならない。
- **測定の自己申告性**：セッションログの `tool_calls` と `files_read` は自己申告であり、完全に検証する手段がない。これらを根拠とする副次指標は目安に留まる。M1（人間の記録＋GitHub の時刻）と出力文字数（X4 実測）は、それぞれ裏付け手段があるため格が違う。
- **取得経路への依存**：数値の見え方は HTML 変換の癖に依存しうる。両アーム共通の条件ではあるが、PDF 原本で読む実務とは難しさが違いうる。真値確定段階 (§8) で確定できない項目は両アーム共通に除外される（ §8）。
- **壁時計の環境変動**：M1 にはプラットフォームの応答速度や CI の待ちが含まれる。両アームに共通する要素が多いとはいえ、投入する時間帯がずれれば混入の仕方も変わる。絶対値としてではなく、同一作業期間内での相対比較として読む。
- **`rho` の推定は目的ではない**（ §0）。両アームに共通する誤り項目の列挙は相関の証拠ではなく、X4 はこの点を結果報告で改めて明示する義務を負う。
