## 2. 最小CIの設計（`.github/workflows/core-check.yml`）

ゲートするのは決定論的・再実行可能な**8検査**（2026-10-21 時点。初版は4検査で、2026-10-20 に 5・6 を、2026-10-21 に 7 を、同日 8 を追加した）：

1. `python3 -m unittest discover -s tests -v` — **559テスト**（約3〜5秒）
2. `python3 gitswarm/benchmarks/benchmark.py --check` — 成果物と fresh run の照合（許容誤差0.01）
3. `python3 gitswarm/readout_sim.py --check` — 投票シミュレーション成果物と fresh run の照合
4. `python3 scripts/validate_state.py` — 研究台帳のスキーマ・ID一意・参照整合性（**台帳内の** ID・パス参照の存在検査を含む）。台帳は**凍結ベース（`state/*.jsonl`）＋セッション別シャード（`state/<台帳名>.d/*.jsonl`）の統合ビュー**として検証される（`scripts/ledger_store.py`）。2026-10-21 から**来歴ゲート**（§2.5）も同じ検査に入った
5. `python3 scripts/check_citations.py` — 台帳書誌と同梱arXivスナップショットの照合（**オフライン・ネットワーク不要**。実API照合の `--live` は手動専用でゲートしない）
6. `python3 scripts/check_memo_citations.py` — 調査メモ（`contributions/*.md`）の参考文献・本文中arXiv引用と同梱スナップショットの照合（オフライン）
7. `python3 scripts/check_memo_ledger_refs.py` — 調査メモ内の**台帳ID参照とリポジトリパス参照の存在検査**（オフライン。2026-10-21 追加。後述 §2.1）
8. `python3 scripts/check_doc_numbers.py` — **文書内の陳腐化した数値の検査**（オフライン。2026-10-21 追加。後述 §2.2）

**計測器（ゲートではない。終了コードは常に 0）**：
`scripts/holdout_eval.py`（§2.3）—— 検査器を dev / hold-out 分割で評価し過適合を検出。
`scripts/prune_candidates.py`（§2.4）—— 低寄与コンポーネントを報告。**何も削除しない**。
いずれも RRSI（`arXiv:2609.24972`）の設計要素の実装である（`docs/literature-triage-2026-10-21.md`）。

設計上の決定：

- **shallow checkoutでよい**：テストは合成リポジトリでreadoutを検証し、本リポジトリの履歴を読まない
- **Python 3.12に固定**（`setup-python`）：ベンチマーク数値の決定性を環境変動から守る。TOLERANCE=0.01と `round()` があるため3.11でも同一値を確認済みだが、CIは固定する
- **readout CLIはゲートしない**：履歴にworkerコミットがない間は exit 1 が正常であり、freshな `main` を赤くする理由にならない（A7の教訓：正常状態を失敗として検出するゲートを作らない）
- **arXiv APIへの実ネットワーク照合はゲートしない**：CIはネットワークなしだけで再実行できる同梱fixture照合（検査4）のみ。`--live` はarXivのレート制限も含め手動実行専用
- **何を足さないか**：trailer検査、役割検査、append-only検査、landゲート、成果物アップロード、動作確認用の計算テスト。これらは凍結であり、欠落ではない

## 2.1 検査7（メモ内の台帳ID・パス参照）を足した理由と限界

**動機**：`contributions/2026-10-20_integrated_survey_report.md` §3.4 が記録した
「理解と生成の非対称」——現在のモデルは複雑な文脈の**理解**には熟達するが、同等に洗練された
**長文の生成**には限界を示す——は、本リポジトリに直接当てはまる。本リポジトリは長文の執筆
（調査メモ・監査文書・統合レポート・PR本文）をエージェントに委任している。

実際に 2026-10-21 までに、エージェントが書いた長文から**機械検査でしか検出できない問題**が
3 件出ている。

| # | 内容 | 検出したもの |
|---|---|---|
| a | 文献メモが arXiv:2605.23950 を「実験を持たない」と記述（実際は自前の 3×3 実験を持つ） | 並列照合セッションの逐語照合 |
| b | context engineering の 3 構成要素を「階層」と記述（原典は平坦な列挙） | 同上 |
| c | メモに記載されたコマンドが存在しないファイル名（日付テンプレート `2026-10-2X`）を指す | **検査7**（本検査） |

**検査7は (a)(b) を検出できない。** これらは意味的な誤りであり、原典と突き合わせなければ
分からない。検査7が検出できるのは**参照が解決しない**こと——存在しない台帳IDの引用
（誤記または幻覚）、存在しないパスの参照——だけである。
**何を検出しないかを明示したうえで置く。** 検出範囲を過大に宣言しない。

**アーカイブ済みIDの扱い**：2026-10-20 に台帳から除いたレコード（CLM-004/005/007 ほか）は
`docs/archived-ledger-records-2026-10-20.md` に原文が残る。統合レポートはこれらを
「除外した」旨の記述で正当に参照しているため、**失敗ではなく ARCHIVED として報告**する。

**`--coverage` はゲートにしない**：どのメモからも参照されていない台帳レコードを報告する機能だが、
新規に起こした EVD は報告へ反映されるまで一時的に未参照になる。
**正常な状態を失敗として検出するゲートは作らない**（A7 の教訓）。

## 2.2 検査8（文書内の陳腐化した数値）を足した理由と限界

**動機（監査 ID 19）**——2026-10-20 の監査は、同じ種類の欠陥を**2 回**別々に検出した。

- **ID 12**：記録された計数（「74テスト」等）が陳腐化していた。 <!-- drift-ok -->
- **ID 14**：本 §4 の DoD が「最小CI（3検査）」と書いている間に、CI は 4 → 6 → 7 → 8 と増えていた。

どちらも原因は同じ——**現在の状態を述べる数値を散文に直書きし、誰も再検証していなかった**。
そしてどちらも**手作業で、事後に**見つかった。検査8はこの欠陥クラスを閉じる。

**何を検査するか**——`scripts/check_doc_numbers.py` は次を**リポジトリから再計算**し、
文書内の記述と突き合わせる。

| 文書内の記述 | 実測元 |
|---|---|
| `合計 N件` / `Nテスト` / `N tests` | `tests/*.py` の `def test_` の静的計数（`unittest` の収集数と一致を確認済み） |
| `test_NAME.py …（N件）` | 当該ファイルの `def test_` 数 |
| `Nゲート` / `N つ）` | `core-check.yml` のステップのうち **`run:` を持つもの**（setup は `uses:` なので除外リストが要らない） |
| `evidence=N` 他（6台帳。`relations` を含む） | 統合ビューのレコード数（凍結ベース `state/<台帳名>.jsonl` ＋ `state/<台帳名>.d/*.jsonl`）。件数の同期は `scripts/sync_doc_counts.py` |

**対象は `README.md` と本ファイルのみ**——監査や統合レポートは過去の記述（「evidence 47 → 48」）に
満ちており、そこを検査すると**正常な状態を失敗として検出してしまう**。
これは A7 の教訓（正常状態を失敗とするゲートを作らない）の直接的な適用である。

**2つの除外規則**——偽陽性を避けるため。

1. **`>` で始まる行は除外**：これらの文書で引用ブロックは叙述（「2026-10-20 に X を行い、
   台帳は evidence=47 になった」）であり、過去のスナップショットであって現在の主張ではない。 <!-- drift-ok -->
   **この規則のため、DoD（§4）は引用ブロックではなく箇条書きで書く**——実際、DoD を `>` で
   書いていたため「7 つ」の陳腐化が検出されなかった。
2. **行内の `drift-ok` で除外**：明示的な escape hatch。

**曖昧性の扱い**——数値は `test_NAME.py` の**出現位置の近傍**（前40文字・後120文字）から読む。
行単位で「テストファイルが複数あれば曖昧として除外」としていた最初の実装は、
`test_minimal_core.py | （28テスト） | …旧 test_integrity.py は不採用` という行で <!-- drift-ok -->
**実ドリフト（28 vs 34）を取り逃した**。近傍方式なら両方を正しく扱える。

**「N件」は日本語の汎用カウンタである**（「候補5件」「fixture追記7件」）。
したがって裸の `N件` は、行に「テスト」という語があるか「合計 N件」の形である場合だけ
件数として読む。この絞り込みを入れる前は、本ファイルだけで**4件の偽陽性**が出ていた。

**限界**——数値の**食い違い**は検出するが、数値の**正当性**は判定しない。
「テストが 205 件ある」ことが正しいかどうか（十分なカバレッジか）は別の問題である。 <!-- drift-ok -->
また対象外の文書（監査・統合レポート）内の数値は、引き続き人手で確認する必要がある。

## 2.3 計測器：hold-out / OOD 分離による過適合検出（`scripts/holdout_eval.py`）

**動機（RRSI）**——RRSI は固定タスク集合でハーネス改善候補を評価するため、
**その集合への過適合**が起きる。対策は、探索を導く指示タスクと、採否を決める
hold-out / OOD 評価を**分ける**ことである。

本リポジトリも同じ形をしている。

| RRSI | 本リポジトリ |
|---|---|
| ハーネス | CI ＋ スクリプト ＋ 文書の書式規約 |
| 固定タスク集合 | 現在のコーパス（メモ・文書） |
| 過適合 | 「ゲートが緑になるまで調整する」 |

**これは仮説ではない。** §2.2 の `check_doc_numbers.py` は、偽陽性を消えるまで
**目の前のコーパスに合わせて**規則を足した（ブロッククォート除外、`drift-ok`、
「N件」パターンの絞り込み）。**その規則が、調整に使っていないファイルにも
 generalizes するかを誰も検査していなかった。**

**何をするか**：

1. コーパスを SHA-256（パス ＋ 記録済みシード）で **dev と hold-out に決定論的に分割**。
   パスを使うので、ファイルが増えても既存ファイルの割当は動かない。
2. 検査器を**分割ごとに別々に**走らせ、検出率を比較。
3. RRSI の失敗モードを検出する——**dev では 0 件、hold-out では検出あり**。
   これは「調整に使った分割でだけ綺麗に見える」検査器である。
4. **採否は hold-out で判定する**（標本外で決めるという RRSI の原則）。

**行レベルへのフォールバック**：`doc_numbers` のコーパスは 2 ファイルしかなく、
ファイル単位では hold-out が作れない。この検査器は**行単位で判定する**ので、
行単位で分割する。**ただし元ファイルごとに分割する**——全ファイルを 1 本に連結すると、
片方の文書の行がもう片方の行の文脈を与えてしまい、**どちらの実文書にも存在しない
検出を捏造する**。

**ゲートにしない理由**：両分割に検出があるのは一部の検査器にとって正常な状態であり、
正常状態を失敗とするゲートは作らない（A7 の教訓）。**計測器であり、終了コードは常に 0。**

## 2.4 計測器：低寄与コンポーネントの報告（`scripts/prune_candidates.py`）

**動機（RRSI）**——RRSI は探索の正則化だけでなく、**価値の乏しいコンポーネントの剪定**
も行う。ハーネスは、コストと注意を食うのに何も寄与しない部品を溜め込む。

本リポジトリも溜め込んできた——3 日で CI は 4 ゲートから 8 ゲートへ、 <!-- drift-ok -->
チェックスクリプトは 1 本から 10 本へ増えた。**どれが居場所を稼いでいるかを
誰も尋ねていなかった。**

**何を測るか**（すべて機械的に決まる）：`in_ci` / `has_tests` / `referenced_in_docs` /
`imported_by`。これらから `keep` / `active` / `weak-candidate` / `candidate` に分類する。

**絶対に削除しない。** 剪定は人間の判断である。ゲートの削除は **`main` が保証する
内容を変える**のであって、掃除ではない。したがって——

- **ゲートは常に `keep`**。警告が出るとしても「専用テストファイルが無い」ことについてだけ。
- 出力は**報告のみ**。削除の API はソースに存在しない（テストで担保：
  `tests/test_prune_candidates.py::test_never_deletes_anything`）。

**曖昧さは解決せず明示する**（機械的には決まらないため）：

1. **検出 0 件の検査器は、自動的には死荷でない。** 抑止力として働いている可能性がある
   ——コーパスが綺麗なのはその検査器のおかげかもしれない。検出 0 件を剪定シグナルにすると
   **「効いている検査器を罰する」**ことになる。ゆえに検出数は**情報として報告するだけで
   判定には使わない**。
2. **網羅はファイル名ではなく内容で判定する。** `validate_state` と
   `gitswarm.benchmarks.benchmark` には `test_<name>.py` が無いが、どちらも
   `tests/test_minimal_core.py` から実行されている。**ファイル名が一致しないだけで
   「テストされていない」と警告するのは偽陽性**だった（初版で実際に出た）。

## 2.5 来歴ゲート：仮説サイクルの記録（2026-10-21 追加）

**動機**——本リポジトリは定量検証（統制実験）を行わない方針を採りうる。その場合に
「検証」の代わりに残るのは**反証可能性の記録**だけである。ところが 2026-10-21 の実測で、
新規 4 仮説の「支持」の **94〜100% が、その仮説の生成に使った証拠そのもの**であり、
関係台帳 241 件の `refute` は **0 件**だった。生成と裁定が同じ材料を共有し、それを
記録する欄がなかったことが原因である。設計は `docs/2026-10-21_hypothesis-cycle-automation.md`。

**追加した台帳**（いずれも凍結ベースは空で開始し、追記はシャードへ）:

| 台帳 | ID | 何を記録するか |
|---|---|---|
| `state/search_log.jsonl` | `QRY` | 実行した検索（クエリ・日時・経路・ヒット数・採用した SRC）。「探して無かった」と「探していない」を区別する |
| `state/runs.jsonl` | `RUN` | ラウンド番号・開始終了・**人間の介入回数**・コスト。自動化率を測るための計測記録 |
| `state/predictions.jsonl` | `PRD` | 観測前に登録した予測（確率・反証条件・登録時刻）。後から条件を緩められないようにする |

**ゲートするのは記録の存在だけ**であり、質の判断はしない。

1. 新規 SRC は `query_id` を持ち、その QRY が `included_source_ids` で逆向きに参照する
2. 新規 HYP は `round` / `derived_from_evidence_ids` / `refutation_condition`（3項目すべて非空）
   / `next_literature_questions`（非空）/ `next_internal_measurements`（存在。空リスト可）を持つ
3. 新規 REL は `derived_from` / `searched_refutation` の真偽値を持ち、`derived_from=true` は
   仮説側の `derived_from_evidence_ids` と一致する

**免除はファイル単位**（`state/cycle_exemptions.json`）。シャードは 1 セッションが 1 回だけ書き、
以後編集しないため、「既知のファイルに無い」＝「新しいレコード」が厳密に成り立つ。
250 件の ID を列挙して保守する必要がない。免除は 2 段ある——`legacy_files`（サイクル機構以前。
全検査を免除）と `pre_split_files`（`next_*` の分割以前。**分割の検査だけ**を免除し、
`round` / `derived_from_evidence_ids` / `refutation_condition` は検査し続ける）。両方に
同じファイルを書くとエラーになる。

**反証可能性の扱い（2026-10-21 追加）**：`refutation_condition.threshold`（`metric` /
`operator` / `value`）は**任意**であり、書けなくても仮説は有効である。これは Phase 1 の
「記録の存在だけをゲートする」方針の延長で、**反証可能性の水準が仮説ごとに違うことを
ゲートで均さず計測値として残す**。ただし書いた場合は型を厳格に検査する（未知の operator・
非数値・bool は失敗）。閾値を持つ `PRD` だけが機械採点の対象になる。

**計測器の出力も台帳に入れる（同日追加）**：`gap_scan` / `holdout_eval` / `prune_candidates`
などの測定を根拠に検索や仮説生成を行う場合、その測定を `SRC-004`（本リポジトリ）起点の
`EVD` として起票する（`quote_type: "measurement"`）。`measurement` 型の EVD 自体は
前例がある（`EVD-20261020-ffec`）が、「測定を検索計画の根拠にするなら EVD にする」と
いう規約の適用第 1 号が `EVD-20261021-d88a`（ラウンド0の自己支持率）である。台帳外の数値を根拠にすると `QRY.derived_from` が空になり、
S0 の「穴に紐づかないクエリは採らない」が空文化するためである。

**何を検出しないか**：支持が汚染されているか（自己支持率）、仮説が良いか、refute が十分か。
いずれも計測器（Phase 3 の `scripts/self_support.py`）が報告し、人間が判断する。
ゲートは「記録が無いこと」だけを失敗させる。

## 2.6 計測器：S0/S7 のクエリ計画（2026-10-21 追加）

**動機**——仮説サイクルの S7 は「`next_observations` と反証条件からクエリを機械生成する。
人が書かない（人が書くと人がボトルネックに戻る）」と定めている。Phase 2 はその生成器
`scripts/next_queries.py` である。

**生成規則は決定的**：小文字化 → 英数字とハイフン以外で分割 → stopword と重複を除去 →
先頭 `--max-terms` 語（既定 10）を連結。モデルもネットワークも使わない。同じ台帳に対して
2 回実行すると同じ出力になる。ハイフン化合物は 1 語として残し、内容語が残らない問いは
空クエリにせず `no_terms` として報告する。

**入力は 2 つ**：仮説レコードの `next_literature_questions`、無ければ overlay
`state/hypothesis_questions.jsonl`（＋シャード）。overlay は分割前のレコードに問いを
足すための sidecar で、`state/evidence_keys.jsonl` と同じ base + parts の形をとる。
**レコードが問いを持つ場合は overlay がそれを影にしてはならない**（エラー）。
`validate_state.py` がこの 2 条件（既知の仮説・非 shadowing）だけを検査する。

**重みは `gap_scan` から取る**：`unresolved` の多い仮説を先に検索し、`unexplained` の
観測は `observation_key` がある場合に限り coverage クエリにする。`unexplained` の定義は
`gap_scan.analyse` をそのまま呼ぶので、計測器と 1 か所で共有される。既に実行したクエリは
`search_log` との完全一致・部分集合一致で `already_searched` に落とし、再提案しない。

**ゲートにしない**：CI 非接続。計画が 0 件でも終了コード 0、台帳を読めないときだけ 2。
生成されたクエリの良し悪しは測っていない（次ラウンドの `hits` / `screened` が測る）。

**初回実測**は 7 仮説・14 クエリ。`unexplained` 25 件のうち `observation_key` を持つものは
**0 件**で、coverage クエリは生成されなかった——未説明観測を検索で攻めるには S3 の注釈が
先に要る、という発見である。詳細は設計 §14 と
`contributions/2026-10-21_phase2_next_queries.md`。
