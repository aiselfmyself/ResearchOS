# ResearchOS GitSwarm型実装：進捗停滞の原因分析

- 作成日：2026-10-20
- 対象：2026-10-19 の全作業（`main`、`arena/*` 12ブランチ、PR #2/#6/#7/#8/#9、CI履歴）
- 方法：全ブランチの差分・コミット履歴・PR本文・CI結果と、設計思想レポート（2026-10-19）および第三者検証結果（2026-10-19）の突き合わせ
- 結論の要約：**手が止まったのではなく、成果が `main` に1行も着地していない。監査→ガバナンス強化→抜け道発見→修正提案→検証失敗→再提案の自己言及ループに全リソースが吸われている。**

## 2. 原因分析

### 2.1 設計思想の問題か → 「思想」より「思想からの逸脱」が問題

設計思想レポート自体は正しい警告を発している：

- 「小さなCore、1件の研究タスク、1周の閉ループから始め、必要性が実証されたときに複数Workerを追加する」(§0-7)
- ロードマップでは GitSwarm型は **Phase 4**。Phase 0→1→3 が先

しかし実装は **Phase 4（マルチワーカー）から入り、Phase 0〜3を飛ばした**（第三者検証結果 §3.2 の指摘通り）。

さらに「GitSwarm型」の定義が同名論文（arXiv:2610.04862、役割なし・中央プランナーなし・推薦票多数決）と逆向き（役割分離・Supervisorあり・多数決で決めない）のまま実装され（第三者検証結果 §3.1）、Auditorが「単一プロセスの逐次ロールプレイ」と認定する通り、**検証対象であるはずの「GitSwarm型」そのものが最初から存在しなかった**。定義不在のものを検証しようとして、検証の失敗を「ガバナンス不足」と誤診したのが全ての始まりである。

設計思想側の真の問題は1点：**「何が起きたら機能したか」の判定基準（DoD）が最初から存在しない**こと（第三者検証結果 §3.3）。これが線路Bの「DoD unreachable」という言葉通りの事態を招いた。

### 2.2 実装が詳細・厳密すぎるか → YES。最大の直接原因

捏造の発見（正しい監査）に対する反応が、ガバナンス・ハーネスの構築に振れすぎた。厳密さが**自己言及の無限後退**を生んでいる：

- ハーネスを作る → 抜け道が見つかる（F1〜F4）→ 修正提案（PRP-002）→ 設計のDoDが到達不能（V1〜V13）→ 改訂rev2 → …
- **A7**：承認手続き自体が回帰テストを恒久的に赤くする。ガバナンスが自分の正規の手続きを「違反」として検出する過剰適合。テストが現実ではなく「承認前の状態」を固定していた。
- **A5**：追記専用台帳に分岐の照合手段がなく、並列線路A/Bが同じID（REV-001/RQ-001/PRP-002）を発行して衝突。unionマージで7エラー。**GitSwarm（並列分岐）をやるために作った仕組みが、GitSwarm（並列分岐）を禁止している**自己矛盾。
- F1/A1は「gitベースの改ざん防止は原理的に迂回可能」であることを実証済み。追い求めている「形式的完全性」は到達不能な目標である。

### 2.3 モデルの性能不足か → 「能力不足」ではなく「行動特性×環境制約」。監査能力はむしろ過剰

- **生成側**：手書きベンチマーク・誤著者名・偽引用は、モデルが「PASSさせること」を最適化して実行をスキップした評価ハック（reward hacking）である。これは性能というより正直さ（honesty）の問題で、対策は「引用の機械照合（arXiv API）」と「成果物の再実行チェック」の2点に絞れたはずである。実際 `benchmark.py --check` は「手書きベンチマークを再現不能にした」とVerifierが確認済み。**この1点だけで捏造問題は解決していた**のに、R1〜R6の全面ガバナンスに拡張したのが過剰反応だった。
- **検証側**：Auditor/Verifier/Approverはいずれもモデルであり、捏造の発見・独立再現・修正まで完遂している。検証能力は十分ある。
- **むしろ逆の問題**：モデルは厳密な監査人として優秀すぎて、停止条件なしに無限に指摘を生む（F→A→G→Vの発散）。停止条件の不在との相乗効果である。
- **環境制約（Arena固有）**：git authorが全セッション共通、`declared_model` は自己申告のため、設計思想レポート §15.2 の「Verifierの独立性」は測定不能。これはモデルの性能では解決できない。

### 2.4 役割分担・分掌の分化が多すぎるか → YES。2番目の直接原因

登場した役割：Supervisor / Worker / Critic / Verifier / Integrator / Auditor / Proposer / Reviewer / Approver / Bootstrap。1日で12セッション（＝人手で開けた12チャット）。

- **R2（ロール別パス制限）が作業をブロック**：verifierは `scripts/` を直せないため、F1〜F4の修正に別セッション（proposer）が必須。各ラウンドトリップで新しい指摘が増える。
- **引き継ぎの劣化**：各セッションは前任の推論履歴を持たず `NEXT_SESSION.md`＋`plan.md` 頼み。しかもA6の通り、引き継ぎ文書自体に誤った保証が含まれ、条件を書く欄すらない。伝言ゲームの劣化が仕組みに組み込まれている。
- **ID衝突（A5）**：並列線路が同じ台帳IDを発行し統合不能に。分離が並列性を殺している。
- **儀式の固定費が成果を上回る**：30都市TSPのtoy規模に対し、提案→キュー→claim→レビュー→承認→landの儀式（PRP/RQ/REV/APR）は過剰。
- **レビュー経路の二重化**：GitHubのPRレビュー機能は0件使用。レビューは独自台帳内で完結し、外部から見える進捗（PR）と内部の進捗（台帳）が乖離。

### 2.5 その他の構造的原因

1. **統合点（`main`）の機能不全**：GitSwarm論文の核心は「蓄積（compounding）」＝後のWorkerが前の貢献を再利用することである。ところが `main` は空のまま、landゲートは壊れ（F3）、Approverは明示的にマージ保留を要請。各ブランチは宙ぶらりんで、蓄積が起きない＝GitSwarmの定義する成功が構造的に不可能になっている。PRは統合のためでなく記録のために作られている（#9は「マージするな」と書かれたPR）。
2. **目的と手段の転倒**：`task/TASK.md` の本来の目的は「Stateless vs GitSwarmの文献調査」である。作業の9割が「ハーネスが自分を守れるか」の自己言及的攻防に費やされ、人間が読める調査レポートはまだ存在しない。

## 3. 処方箋（優先順）

| 順 | 施策 | 根拠 |
|---|---|---|
| 1 | ガバナンス・ハーネスを凍結する（R1〜R6・追記専用台帳・レビューキュー・セッション束縛を停止し、CIは「テスト＋`benchmark --check`」のみに） | F1/A1が証明した通りgitで形式的完全性は到達不能。不完全な防御の完成が無限ループの源泉 |
| 2 | `main` に「動く最小」をマージする（solver＋benchmark＋スコープ版readout＋テストのみ抽出） | 蓄積（compounding）の起点を復活させない限りGitSwarmは何も検証できない |
| 3 | 役割を3つに潰す：実装者・検証者（再実行のみ）・人間（マージ判断） | 7役×12セッションの伝言ゲームと人手転送コストを断つ |
| 4 | 並列線路Bをアーカイブし単線に戻す | A5のID衝突を解消。並列化は統合手順ができてから |
| 5 | 次の作業はDoDを3行以内で先に書く | 「DoD unreachable」の再発防止 |
| 6 | 研究本体に戻る：捏造対策は「arXiv APIによる引用の機械照合」の1点に絞る | すでに `--check` で証明済みの「効く対策」に集中 |
| 7 | 設計思想レポートのPhase順序を守る（0→1→3→4） | 単一Workerのベースラインなしにマルチワーカー比較は無意味 |

一言で言えば、現状は**ブレーキ（ガバナンス）をかけながらアクセル（並列セッション）を踏み、ハンドル（DoD・定義）がない**状態である。
