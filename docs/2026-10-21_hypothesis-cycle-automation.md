# 定量検証を外した「仮説サイクル」の自動化設計

- 作成日：2026-10-21
- 種別：設計メモ（**実験の実行を含まない**。数値はすべて 2026-10-21 時点の実測、見込みは推定と明記する）
- 対象：`task/TASK.md` の研究を「実験・定量検証なし」で回す場合に、どこまで自動化でき、何を先に作るか
- 前提：本リポジトリの現在地の評価は会話（2026-10-21）で行った。台帳は sources=23 / evidence=88 / claims=9 / verifications=40 / hypotheses=6 / relations=241、テスト 437 件、CI 8 ゲート

---

## 0. 結論（先に3行）

1. **可能。ただし「定量検証を捨てる」と「検証を捨てる」は別である。** 捨てられるのは統制実験と統計的有意性であり、捨てられないのは**反証条件**である。反証条件を捨てた瞬間、この研究は「文献の要約生成」に退化する。
2. **律速は知能ではなく配線にある。** 台帳は既に「次に集めるべき観測」を仮説の `notes` に持っている（`HYP-20261021-*` の 4 件）。しかし**それを読んで次の検索クエリを作る機械が存在しない**。8 工程のうち 5 工程は機械化でき、残り 3 工程は LLM の 1 セッションで足りる。
3. **既に循環の証拠が出ている。** 新規 4 仮説の「支持」のうち **94〜100% が、その仮説の生成に使った証拠そのもの**による支持である（実測・§2.3）。自動化はこの循環を増幅する。**hold-out 証拠の規律を、仮説生成の自動化より先に入れなければならない。**

## 1. 「定量検証を捨てる」で何が失われ、何で代替できるか

| 失うもの | 代替するもの | 代替の強さ |
|---|---|---|
| 因果の同定（統制実験） | **何も代替できない。** 因果主張を書かない、と明示する | 代替不可。主張の格を下げるしかない |
| 効果量の実測 | **メタ分析**：既存論文の報告値を版固定で抽出し、効果量・信頼区間を統合する | 中〜強。実験不要で定量が残る唯一の経路 |
| 統計的有意性 | **予測の事前登録**：仮説ごとに「どの観測が来たら反証か」を先に書く | 中。当たれば弱い確証、外れれば強い反証 |
| 再現性 | **逐語照合**：引用文が原典に存在することを機械で検査（既存ゲート） | 強（捏造のみ）。意味の正しさは保証しない |
| 妥当性 | **文献間の矛盾の検出**：同じ量を別々に測った報告を突き合わせる | 中。本リポジトリの `R` 論争が実例 |

**残せる定量（実験なしで測れる数）**は 5 つある。これは「定量を捨てる」のではなく「実験を捨てる」と読み替えたときに残る資産である。

1. **カバレッジ**：`unassessed / unexplained / unresolved` の比率（現状 unexplained 21/88 = 23.9%）
2. **裁定の一致率**：同じ証拠を 2 回裁定して一致するか（LLM の再現性）
3. **自己支持率**：仮説の支持のうち、生成に使った証拠によるものの割合（§2.3）
4. **新規性**：ラウンド当たりの「既存仮説と重複しない新仮説」の数
5. **コスト**：ラウンド当たりのトークン・セッション時間・人間介入回数

**この 5 つを記録しない限り、自動化率は永久に測れない。** SVM 実験（`contributions/2026-10-21_svm_results.md`）が「投入時刻が未記録で壁時計が代理値」になったのと同じ失敗を、ループ全体で繰り返すことになる。

### 2.2 台帳が既に持っているが、誰も消費していない情報

- `hypotheses[*].notes` の「**次に集めるべき観測**」（4 件、具体的な実験・計測の記述つき）
- `hypotheses[*].notes` の「**反証条件**」（4 件）
- `verifications[*].suggested_actions`（未集計）
- `relations` の `unresolved` 18 件（何が決まっていないかの一覧）
- `gap_scan --json` の `unexplained` 21 件（どの仮説も説明していない観測）

**これらは検索クエリに変換できる形で既に書かれている。** 変換器がないだけである。

### 2.3 危険信号：新規仮説の支持は「自分の根拠」でほぼ埋まっている

`state/relations*.jsonl` と `state/hypotheses*.jsonl` の突き合わせ（2026-10-21 実測）。

| 仮説 | support | neutral | unresolved | 支持のうち生成元 EVD によるもの |
|---|---:|---:|---:|---:|
| HYP-001（原初） | 12 | 65 | 11 | 3/12 = **25%** |
| HYP-002（原初） | 11 | 73 | 4 | 2/11 = **18%** |
| HYP-20261021-9f99 | 17 | 0 | 2 | 16/17 = **94%** |
| HYP-20261021-fee7 | 25 | 0 | 0 | 25/25 = **100%** |
| HYP-20261021-4cdb | 12 | 0 | 0 | 12/12 = **100%** |
| HYP-20261021-a10b | 8 | 0 | 1 | 8/8 = **100%** |

全体では `refute` が **0 件**（241 件中）。verdict の内訳は neutral 138（57%）、support 85（35%）、unresolved 18（7%）。

**読み方**：原初の 2 仮説は neutral が 65〜73% あり、「証拠の大半はこの仮説に何も言っていない」と正しく記録されている。新規 4 仮説は**支持だけ**で、しかもその支持は**生成に使った証拠**である。これは仮説生成と裁定を同じ材料で行ったことの必然的な帰結であり、**証拠の独立性がゼロ**である。

自動仮説ループをこのまま回すと、**「証拠から仮説を作り、その証拠で支持する」機械**が高速に回り、支持件数だけが増える。これは研究成果ではなく、**循環の生成装置**である。

## 3. 8 工程のループ設計

```
        ┌──────────────────────────────────────────────────────────┐
        │                                                          │
        ▼                                                          │
  S0 検索計画 ── S1 検索 ── S2 選別 ── S3 精読・抽出 ── S4 関係裁定 │
   (機械)        (LLM)      (LLM×2)     (LLM)            (LLM×2)    │
        ▲                                                          │
        │                                                          ▼
  S7 クエリ生成 ◀── S6 予測登録 ◀── S5 仮説生成 ◀───────────────┘
   (機械)            (LLM＋機械)       (LLM)
        │
        └──► S8 ラウンド報告（LLM）──► 停止判定（機械）
```

各工程の「入力・出力・主体・ゲート・固有の失敗モード」を以下に定める。**主体が「機械」の工程は CI でゲートでき、「LLM」の工程はゲートできない**——この区別が設計の骨格である。

### S0 検索計画（機械）

- **入力**：`gap_scan --json` の `unexplained`、`relations` の `unresolved`、`hypotheses[*].notes` の「次に集めるべき観測」、`verifications[*].suggested_actions`
- **出力**：検索クエリ集合（`{query, 由来ID, 種別, 優先度}`）
- **由来ID は必須**。「思いつきのクエリ」を禁じ、**台帳の穴に紐づかないクエリは採用しない**
- **失敗モード**：クエリが同じ語の繰り返しになり、同じクラスタに閉じる → §7-2 の 3 系統検索で防ぐ

### S1 検索（LLM、記録は機械）

- **制約（実測済み）**：**サンドボックスから arXiv API へは到達できない**（`urllib` で TLS が閉じる。2026-10-21 実測）。到達できるのは agent の web 検索・fetch だけである。したがって**検索は必ず LLM セッションの工程**であり、cron で回すことはできない
- **出力**：`state/search_log.d/*.jsonl` に 1 クエリ 1 レコード（`query, api, executed_at, hits, screened, included, excluded_reason`）
- **ゲート**：検索ログなしに SRC を追加できない（後述 §5 の検査 1）
- **失敗モード**：検索していない文献を「見つからなかった」と書く → ログ必須で防ぐ

### S2 選別（LLM を 2 回、独立に）

- **包含基準を先に固定**してから検索する（後から基準を作ると、見つかったものに合わせて基準が動く）
- タイトル＋抄録のみで判定。判定は 2 セッション独立。**一致しないものは「保留」**とし、無理に決めない
- **測るもの**：一致率。低い基準は基準として機能していない

### S3 精読・抽出（LLM）

- **項目は固定スキーマ**（SVM 実験の 51 項目方式を流用）。自由記述を許すと、後で比較できない
- **`excerpt` は原典の逐語**。要約を excerpt 欄に入れない（既存の `check_memo_citations` が arXiv ID しか見ないので、逐語性は別途 S3 の規約で守る）
- **版を固定**（版付き URL。`docs/literature-triage-2026-10-21.md` で版ずれが 2 回起きている）
- 見つからない項目は棄権（`null`）。**推測で埋めない**

### S4 関係裁定（LLM を 2 回、独立に）

- 4 値（support / refute / neutral / unresolved）は既存スキーマのまま
- **追加する規律（最重要）**：`derived_from = true` の証拠は、**support の集計から除外する**。仮説を生成するのに使った観測は、その仮説の証拠にならない（§2.3 の循環を構造で断つ）
- **`refute` を必ず 1 回は探す**。「反駁が見つからない」と「探していない」を区別するため、裁定時に `searched_refutation: true/false` を記録する

### S5 仮説生成（LLM）

- **トリガーは機械が決める**：`unexplained` が閾値を超えた観測、または `unresolved` が 2 ラウンド続いた関係
- **テンプレート**：「観測 O（EVD-x, EVD-y）を説明する H」
- **必須フィールド**（後述のスキーマ拡張）：
  - `derived_from_evidence_ids`：生成に使った観測（**これが hold-out の分母になる**）
  - `refutation_condition`：機械可読な反証条件
  - `next_observations`：次に集める観測（既に `notes` に散文で存在するものを構造化）
- **失敗モード**：既存仮説の言い換えを「新規」と数える → 重複判定（文の類似度＋`derived_from` の一致）を機械で行う

### S6 予測登録（LLM＋機械）

- 反証条件を「観測の型」に落とす：例 `{metric: "ranking_reversal_count", condition: "== 0", dataset: "...", model_gap: "R<1"}` 
- **事前登録の時刻を記録**する。後から条件を緩められないようにする（`pre_registered_at` と、条件を変更した場合の `superseded_by`）
- これは実験なしで反証可能性を確保する唯一の手段である

### S7 クエリ生成（機械）

- `next_observations` と `refutation_condition` からクエリを機械生成する
- **人が書かない**。人が書くと、人がボトルネックに戻る
- 生成規則は単純でよい：観測の対象（データセット・指標・モデル群）× 反証条件の語 × 論文種別

### S8 ラウンド報告（LLM）と停止判定（機械）

- 報告は**差分のみ**（前ラウンドからの新規 SRC/EVD/HYP/REL と、覆った判断）
- 停止条件（機械）：
  - 3 ラウンド連続で新規仮説 0
  - `unexplained` が減らない
  - `refute` が 0 のまま支持だけ増える
  - 予算（トークン・人間介入回数）超過

## 5. 先に入れるべき 3 つの検査（ゲートにしてよい）

1. **検索ログなしの SRC 追加を拒否**（`search_log` に該当クエリが無い SRC は fail）
2. **`derived_from_evidence_ids` の無い仮説を拒否**
3. **`refutation_condition` の無い仮説を拒否**

この 3 つは「現在の状態を失敗として検出する」ものではなく、**記録の欠落を検出する**ものである。ゲートの意味論を変えない。

逆に、**「自己支持率が高い」ことを fail にしてはいけない**。それは研究の質の判断であり、人間の仕事である（`prune_candidates.py` と同じ立場）。

## 6. 自動化率の見込みと測り方

### 6.1 定義

```
実質自動化率 = 1 −（人間の介入時間 ÷ ラウンド総時間）
介入回数率   = 1 −（人間の介入回数 ÷ 意思決定イベント数）
```

2 つを併記する。時間は自己申告になりがちなので、**回数を主指標**にする（SVM 実験の教訓）。

### 6.2 見込み（推定）

| 段階 | 実質自動化率 | 根拠 |
|---|---:|---|
| 現在 | **20〜25%** | ラウンド間が完全に手作業 |
| §4.2 の 1〜6 を入れた後 | **35〜40%** | 記録が揃い、停止条件が機械化される。ただし検索と仮説生成は人間が起動 |
| S0/S7 と二重裁定を入れた後 | **50〜60%** | 「次に何を読むか」が台帳から出る。ここが最大の跳ね |
| それ以上 | **不可（現構成）** | arXiv API にプログラムから到達できず、モデル呼び出しがチャットセッションである以上、**起動は人間**。API 課金とオーケストレータを用意すれば 80% は可能だが、それは別のシステム |

**楽観シナリオでも 6 割**、というのが正直な線である。ただし「6 割」は現在の 2 割強から見れば**3 倍**であり、ラウンド当たりの人間の関与が「テーマ決定と最終承認の 2 回」に減ることを意味する。

### 6.3 毎ラウンド記録する 6 指標

| 指標 | 定義 | 現在値 |
|---|---|---|
| 人手介入回数 | 人間が判断した回数（`runs` に記録） | 未記録 |
| 新規仮説数 | 重複除去後 | 4（1 回のバッチ） |
| unexplained 率 | `gap_scan` | 23.9% |
| 自己支持率 | support のうち `derived_from` | **新規 4 件で 94〜100%** |
| refute 件数 | 関係台帳 | **0** |
| 裁定一致率 | 二重裁定の一致 | 未測定 |

## 7. 固有の失敗モードと対策

| # | 失敗モード | なぜ起きるか | 対策 |
|---|---|---|---|
| 1 | **自己支持の循環** | 生成と裁定が同じ材料 | `derived_from` を support 集計から除外（§2.3 の実測が根拠） |
| 2 | **検索の閉鎖** | 引用の雪だまりは同じクラスタに閉じる | 3 系統を必ず混ぜる：キーワード検索／引用・被引用／レビュー論文。**新規ソース率**（既存 SRC と引用グラフが重ならない割合）を測る |
| 3 | **neutral の堆積** | 仮説が観測可能な形で書かれていない（現状 57%） | 仮説に `observation_signature` を要求。書けない仮説は仮説ではない |
| 4 | **refute 0 の常態化** | 反駁を探していない | `searched_refutation` を必須にし、0 が続く仮説を「棄却候補」として報告 |
| 5 | **裁定の非再現** | LLM の判断は揺れる | 二重裁定＋一致率の記録。**一致率が低い基準は基準ではない** |
| 6 | **メタ作業の膨張** | 監査・設計・割当が研究を食う（既に docs 9,524 行 vs 研究 4,796 行） | 1 ラウンド 1 文書まで。既存文書は機械同期（`sync_doc_counts.py`）のみ。**新しい規約文書を作らない** |
| 7 | **幻覚引用** | 長文生成の弱さ（統合レポート §3.4） | 逐語 excerpt ＋スナップショット照合（既存） |

## 8. 実質的に研究が進むための追加提案

質問の「その他」に対する提案。**上から順に効く。**

### 8.1 問いを 1 つに絞る（最優先）

現在の問いは少なくとも 4 つある：SLA vs GitSwarm、ハーネス効果 R、共通モード障害、仮説サイクルの設計。**1 つの論文として成立するのは 1 つだけ**である。文献ループは問いが広いと発散し、狭いと収束する。`task/TASK.md` を 1 問いに書き換え、残りは「付録の観察」に落とすべきである。

推奨は **「エージェントの性能差はモデルかハーネスか（R の regime）」**。理由：(a) 既に 3 例のデータ点がある、(b) 反証条件が明確、(c) 実験なしでも文献メタ分析で定量が出せる。

### 8.2 「反証された仮説」を成果として公開する

現在 `refute` は 0 件で、これは「反駁が無い」ではなく「探していない」。**反駁を 1 件出すこと自体をラウンドの成果**にすれば、ループの目的関数が変わる。反証は査読でも最も価値がある。

### 8.3 査読論文を 1 本入れる

23 ソースすべてがプレプリントである。外部接地がゼロのままでは、どれだけ内部整合を高めても「 preprint の要約」を出ない。**1 本でよい**。ACM/IEEE/NeurIPS のサーベイを 1 本入れ、そこから逆方向に 3 本辿るだけで、引用グラフの偏りが大きく変わる。

### 8.4 実験の代わりに「メタ分析」を 1 本やる

これが**定量を捨てずに定量を残す唯一の方法**である。具体的には：

- 対象：エージェント性能を「モデル×ハーネス」で報告している論文
- 抽出：モデル数、ハーネス数、分散分解の有無、順位逆転の有無、タスク領域
- 出力：R（モデル間/ハーネス間の広がり比）の分布と、タスク領域による違い
- これは**実験なしで、既存の報告値だけで成立する定量研究**である。現在の `harness_regime.py` は 3 例の手計算なので、これを N 例に拡張する

### 8.5 予測に確率を付け、後で採点する

各仮説に「次のラウンドで支持が出る確率」を事前登録する。3〜5 ラウンド後にキャリブレーション（Brier スコア）を計算する。**これだけで「AI は自分の仮説をどれくらい当てられるか」という新しい定量が生まれる**。実験装置は不要で、台帳と採点だけである。

### 8.6 出力の受け手を決める

誰が読むレポートか（自分／共同研究者／投稿原稿）で、必要な厳密さが変わる。現在の文書は「監査役としての自分」に向いており、外部読者には読めない（README が 23KB・訂正追記 11 箇所）。**受け手を「1 人の外部研究者」に固定**し、その人だけを読者にした 10 ページの報告を 1 本作る。

### 8.7 unresolved を「資産」として扱う

`unresolved` 18 件と `unexplained` 21 件は、**まだ誰も説明していない観測**である。これはこのリポジトリで最も価値の高い在庫であり、いまは誰も読んでいない。**各ラウンドの最初にこの 39 件を読み返す**だけで、S0 のクエリは自然に出る。

## 10. この設計が主張しないこと

1. **因果**。定量検証を外す以上、因果主張はできない。できるのは「文献間の整合／矛盾」と「予測の当たり外れ」までである。
2. **自動化率の数値**。§6.2 は推定であり、実測ではない。Phase 4 で初めて測れる。
3. **文献のみのループが新規性を生むこと**。引用ネットワークに閉じたループは、既存の言い換えを生成しやすい。§7-2 と §8.3 はその防御であり、防御が効く保証はない。
4. **現在の相対順位**（どの工程がどれだけ自動化されているか）は、実測ではなく筆者の推定である。`runs` 台帳が入るまでは測れない。

### 11.7 記録の書き方（最小例）

新しい文献を 1 本足すとき、**先に検索を記録し、次に文献を記録する**。両方は同じシャードに置いてよい。

```jsonc
// state/search_log.d/2026-10-21-<12hex>.jsonl
{"query_id": "QRY-20261021-a1b2", "query": "harness variance agent benchmark",
 "executed_at": "2026-10-21", "channel": "keyword", "api": "arxiv abs via web fetch",
 "hits": 12, "screened": 5, "included_source_ids": ["SRC-20261021-c3d4"],
 "derived_from": ["HYP-20261021-9f99"]}

// state/sources.d/2026-10-21-<12hex>.jsonl
{"source_id": "SRC-20261021-c3d4", "title": "...", "authors": ["..."], "year": 2026,
 "url": "https://arxiv.org/abs/2610.xxxxx", "type": "preprint",
 "query_id": "QRY-20261021-a1b2"}
```

仮説を立てるときは、**生成に使った観測・反証条件・次に集める観測**を同時に書く。

```jsonc
// state/hypotheses.d/2026-10-21-<12hex>.jsonl
{"hypothesis_id": "HYP-20261021-e5f6", "statement": "...", "status": "proposed",
 "round": 1,
 "derived_from_evidence_ids": ["EVD-20261021-aaaa", "EVD-20261021-bbbb"],
 "refutation_condition": {
   "observable": "同一ベンチマーク・同一予算でモデル群×ハーネス群を直交させる",
   "would_refute": "R<1 の領域で順位逆転が有意に生じない",
   "expected_if_true": "R<1 の領域で順位逆転が生じる"},
 "next_observations": ["SWE-bench 以外で R<1 となる第3のベンチマーク"]}
```

裁定では、**その観測が生成元かどうか**と、**反証を探したかどうか**を必ず書く。

```jsonc
// state/relations.d/2026-10-21-<12hex>.jsonl
{"relation_id": "REL-20261021-1234", "hypothesis_id": "HYP-20261021-e5f6",
 "observation_id": "EVD-20261021-aaaa", "verdict": "support",
 "derived_from": true, "searched_refutation": true,
 "rationale": "生成に使った観測。支持として集計しない"}
```

`derived_from: true` の関係は**支持の集計から外す**。これが §2.3 の 94〜100% を構造的に断つ仕掛けであり、Phase 3 の `self_support.py` はこのフラグだけを見て自己支持率を算出する。

## 13. Phase 2 の前提整備（2026-10-21、修正のみ）

§12.3 の「§12.1 の 1〜3 を直す」を実行した。**新しいラウンドは回していない。**
詳細と実測は `contributions/2026-10-21_phase2_prerequisites.md`。

### 13.1 直した 4 件と、その理由

| §12.1 | 修正 | 直さないと Phase 2 で何が起きるか |
|---|---|---|
| 1 | `next_observations` → `next_literature_questions`（非空）/ `next_internal_measurements`（存在・空可） | S7 の入力が「文献で答えられない実験案」のまま。検索語を抜く文字列処理になる |
| 2 | 計測器の出力を `SRC-004` 起点の `EVD` として起票（`quote_type: "measurement"`） | `QRY.derived_from` が空のまま。S0 の「穴に紐づかないクエリは採らない」が初回から空文化する |
| 5 | `refutation_condition.threshold`（任意・metric/operator/value） | 反証条件が文章のままで、S6 が `PRD` に昇格できるかを機械が判定できない |
| 6 | `gap_scan` が既定で `derived_from` を支持から除外（`--include-derived-from` で旧来） | 新仮説の support が生成元で埋まり、Phase 3 の `self_support.py` と同じ誤りを計測器が再生産する |

### 13.2 閾値は任意、検査は厳格、ゲートにはしない

`threshold` は**書けなくても仮説は有効**である。書かなければ「機械検証不能」という事実が
残るだけで、記録の欠落ではない。一方、**書いた場合は型を厳格に検査する**
（`metric` 非空文字列、`operator` は `<` `<=` `>` `>=` `==` `!=` の 6 種、`value` は数値で
bool を除く）。壊れた閾値は閾値が無いより悪い——検査可能に見えて検査不能だからである。

この非対称（任意だが、書いたら厳格）は Phase 1 の「記録の存在だけをゲートする」方針の
延長にある。**反証可能性の水準が仮説ごとに違うことを、ゲートで均すのではなく計測値として残す。**

`threshold` を持つ `PRD` だけが機械採点の対象になる。既存の `PRD-20261021-1f70` は
文章で同じ内容を述べているが、登録済みの予測を後から書き換えない（`superseded_by` を使う）。

### 13.3 免除を 2 段にした（`legacy_files` / `pre_split_files`）

分割前の記録（ラウンド1の `HYP-20261021-00b4`）は旧 `next_observations` しか持たない。
ここでファイル全体を免除すると、`round` / `derived_from_evidence_ids` / `refutation_condition`
の検査まで外れる——**その 3 つを実演している唯一のレコード**の検査を落とすのは後退である。

そこで `state/cycle_exemptions.json` に `pre_split_files` を足し、`next_*` の分割だけを
免除する。両リストに同じファイルを書くとエラーにする（曖昧な免除を作らない）。

**残る限界**：`HYP-20261021-00b4` と免除ファイルの 5 仮説は `next_literature_questions` を
永久に持たない。Phase 2 のプランナは**未設定を報告してスキップ**すること。空リストと同じ
扱いにすると、「問いが無いのに検索した」記録が生まれる。

### 13.4 `gap_scan` の数え方を変えた結果（数字が悪化したのではない）

| 対象 | 修正前 | 修正後 |
|---|---:|---:|
| `HYP-20261021-00b4` の support | 3 | **0**（うち生成元=3） |
| `unexplained` | 22 / 92 | **25 / 93** |

`unexplained` が増えたのは、**生成元からの支持しか持たない 2 件**が正しく
「独立には説明されていない」と数えられるようになったためである。`derived_from` を
持たない既存 241 関係は false と解釈されるので、既存仮説の support は変わらない
（実際 `HYP-001` 12・`HYP-002` 12 は不変）。旧来の数え方は
`--include-derived-from` で再現でき、両者の和が旧値に一致する。

**残る限界**：`derived_from` はラウンド1以降の記録にしか無い。ラウンド0の関係は
フラグを持たないため、既存 4 仮説の support（9f99=17 / fee7=25 / 4cdb=12 / a10b=8）は
**生成元を含んだまま**である。遡って同定する材料（生成に使った EVD は仮説の
`evidence_ids` にある）は揃っているが、それは Phase 3 の `self_support.py` が行う。
`gap_scan` に推測を入れない——推測でフラグを立てるとゲートが「記録が無い」ことを
検出できなくなる。

### 13.5 Phase 2 に進める状態か

**進める。** 入力（`next_literature_questions`）・動機の ID（`EVD-20261021-d88a`）・
採点可能性の区別（`threshold` の有無）・独立支持の数え方（`gap_scan`）が揃った。
`next_queries.py` は `next_literature_questions` を入力に、`gap_scan --json` の
`unexplained` と `unresolved` を重みとして使う。**未設定の仮説は報告してスキップする。**
