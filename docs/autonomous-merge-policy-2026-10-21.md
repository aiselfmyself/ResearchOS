# 自律マージ方針（2026-10-21）

- 作成日：2026-10-21
- 目的：セッションが**人間のマージ承認を待たずに作業を `main` に取り込む**範囲を定め、
  あわせて**自発的にやってはならない操作**を明示する
- 強制：**なし**。CI はこの文書を実行しない。違反を検出・拒否・記録する仕組みは持たない
- 関連：`docs/parallel-work-ownership.md` §2（所有マップ）、
  `docs/minimal-core-and-ci.md` §3（CI の 6 ゲート）、
  `docs/incomplete-work-audit-2026-10-20.md` §13.8(3)（本方針の決定経緯）

---

## 1. 何を定めるか

人間の相談：「一部の AI がエラーを起こしていたとしても、別の AI による検証＆修正が可能な
ようなので、人間判断によるマージを待たずに、各 AI は作業が完了次第すぐにマージする方向へ
変更できるか。また本リポジトリは研究のみに限定され、現実世界での不可逆的な操作を伴わない。」

**結論：マージについては採用する。ただし破壊的操作は対象外とする。**

| 操作 | 人間の承認 | 根拠 |
|---|---|---|
| CI が緑の PR の `main` へのマージ | **不要**（自発的に実施してよい） | 取り消しが安価。§3 |
| リモートブランチの削除 | **要る** | 到達不能なコミットを生む。§4 |
| `--force` を伴う push | **要る** | 履歴を書き換え、他人の作業を消しうる |
| 台帳レコード（`state/*.jsonl`）の**追記** | **不要**（自発的に実施してよい） | 取り消しが安価。CI（ゲート4・5）が構造と書誌を機械的に検査する。`docs/parallel-work-ownership.md` §2.1 |
| **ID の採番**（`python3 scripts/new_id.py`） | **不要** | 非連番IDが衝突を原理的に避ける。`docs/record-id-scheme.md` §2 |
| 台帳レコード（`state/*.jsonl`）の**削除・書き換え** | **要る** | 追記専用という前提を壊す。再現性の根拠が失われる。訂正は追記（`correction_note`）で残す |
| リポジトリ設定・CI 定義の変更 | **要る** | 全セッションに効く。誤りが波及する範囲が最大 |

**「追記」と「書き換え」の区別がすべてである。** 追記は履歴を追加する操作であり、既存のコミットも既存のレコードも消さない。
書き換えはそうではない。本表の「不要」は追記と採番にのみ適用され、書き換えには適用されない。

## 2. 自発的にマージしてよい条件

次の**すべて**を満たすとき、セッションは人間の承認を待たずに `gh pr merge` してよい。

1. **CI が緑である**（`gh pr checks` がすべて `pass`）。
   本リポジトリの CI は 8 ゲート——`unittest`・`benchmark --check`・`readout_sim --check`・
   `validate_state.py`・`check_citations.py`・`check_memo_citations.py`・
   `check_memo_ledger_refs.py`・`check_doc_numbers.py`
   （2026-10-21 時点。本節は初版から数が変わっていたため、同日に訂正した）。
2. **`MERGEABLE` / `CLEAN` である**（コンフリクトがない）。
3. **PR 本文に、何をしたかと検証結果を明記している。**
   マージが人間の目を通らない分、**後から読む者が判断できる材料**を PR に残す義務が生じる。
4. **破壊的操作を含まない**（§1 の表の「要る」側に触れていない）。

緑でなければ**マージしない**。ここは従来どおりである。

## 3. なぜマージは自発的にしてよいか

**取り消しのコストが低いから**である。

- `git revert` で 1 コミットとして取り消せる。
- 取り消さずに**修正を重ねる**こともできる。実際に本リポジトリでは、並列照合セッションが
  文献メモの事実誤り 2 件を捕捉し、統合役が訂正した
  （`docs/incomplete-work-audit-2026-10-20.md` §13.7(1)）。
  **「誤りが混入する」ことと「誤りが残る」ことは別であり、後者は別セッションが防げる。**
- マージは履歴を**追加**する操作であり、既存のコミットを消さない。

人間の相談が挙げた 2 つの論拠——「別の AI が検証・修正できる」「研究限定で現実世界の
不可逆的操作を伴わない」——は、この範囲では妥当である。

## 4. なぜ破壊的操作は対象外か

**取り消しのコストが非対称に高いから**である。本リポジトリに実例がある。

2026-10-21、`arena/*` のリモートブランチ 36 本を整理した際、1 本ずつ `main` と比較した
（`gh api repos/.../compare/main...<branch>`）。結果は 2 群に分かれた。

| 群 | 本数 | 状態 |
|---|---|---|
| `main` に完全包含（`ahead=0`） | 23 | 固有コミットなし。削除しても何も失われない |
| `main` と分岐（`ahead=2〜61`） | 13 | **固有コミットあり。削除で到達不能になる** |

もし `ahead` を確認せずに「36 本すべて stale だろう」として一括削除していれば、
**PR の存在しない 8 本の孤立ブランチが持つ 33〜61 個の固有コミットを無自覚に失っていた。**
これらは 2026-10-19 の停滞期（`docs/stagnation-analysis-2026-10-20.md`）と
2026-10-20 の並列実験の生データに当たる可能性が高かった。

のちに人間は削除を選択し、ブランチは `main` のみになった
（`docs/incomplete-work-audit-2026-10-20.md` §13.8(1)）。**これは人間の明示的な判断に基づく
対応であり、統合役が自発的に行ってよかったものではない。**

**教訓**：破壊的操作の前には、まず non-destructive な保全手段を検討する
（ブランチを消すなら先に `git tag` を打つ、レコードを消すなら先に退避ファイルへ写す）。
本件では事前にタグを打つべきだった。

## 5. この文書が解決しないもの

`docs/parallel-work-ownership.md` §4 と同じ構造の限界がある。

| 問題 | この文書 | 状態 |
|---|---|---|
| セッションが CI 緑を待たずにマージする | 条件を §2 に定めるが、**強制力はない** | **運用回避のみ** |
| セッションが破壊的操作を自発的に行う | 「要る」と定めるが、検出しない | **運用回避のみ** |
| 誰が変更したかの識別 | 何もしない。全セッションが同一 git author のまま | **未解決** |
| 誤りが混入すること自体の防止 | 何もしない。**混入後の検出と訂正**に賭ける設計 | **意図的に未解決** |

「運用回避」は「解決」ではない。表記を混ぜない。

とくに最後の行が重要である。本方針は「誤りが入らない」ことを目指さない。
**「入った誤りが、別セッションの検証で見つかり、訂正される」こと**を前提に
スループットを上げる選択である。この前提が崩れた——たとえば一定期間、
誰も他セッションの成果物を検証しなかった——場合は、方針を見直すべきである。

## 6. 前提の監視

本方針が安全であるための前提は**「別のセッションが検証する」**ことであり、
これは自動的には保証されない。したがって次を記録する。

- 2026-10-20〜21 の実績：並列照合セッション S1/S2/S3 が計 48 claim を照合し、
  **事実誤り 2 件を捕捉**した（いずれもメモの記述が原典と食い違うもの）。
  統合役が裁定し、人間の承認を得て訂正した。
- 同じ期間に、CI が**機械的な誤りを 1 件**捕捉した（除外済みパスへの参照。
  `docs/incomplete-work-audit-2026-10-20.md` §13.7(2)）。
- **照合を止めれば、この前提は消える。** 検証の実施は各セッションの判断に委ねられる。

## 7. 手順

```sh
# 1. CI が緑であることを確認する（緑でなければマージしない）
gh pr checks <n>

# 2. コンフリクトがないことを確認する
gh pr view <n> --json mergeable,mergeStateStatus --jq '"\(.mergeable) \(.mergeStateStatus)"'

# 3. マージする
gh pr merge <n> --merge
```

破壊的操作をしたいときは、**§1 の表で「要る」側に該当しないかを確認し、
該当するなら人間に判断を仰ぐ。** 判断材料（何本・何コミットが失われるか等）を
添えて提示すること。
