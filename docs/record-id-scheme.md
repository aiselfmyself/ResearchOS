# レコードID方式（非連番ID）

- 作成日：2026-10-20
- 目的：並行作業時のID衝突を原理的に避ける
- 強制：`scripts/validate_state.py` が検査し、CI（`core-check.yml`）で赤になる

---

## 1. 何を変えたか

`state/*.jsonl` のIDは連番（`SRC-001`、`EVD-014` …）だった。連番は**同じ台帳に2つのブランチが追記すると必ず衝突する**。どちらも同じ `max(ID)` を読み、同じ次の番号を採番するためである。

2026-10-20 以降に追加するレコードは、次の形式を使う。

```text
PREFIX-YYYYMMDD-xxxx      例: EVD-20261020-9f2c
```

- `PREFIX`：`SRC` / `EVD` / `CLM` / `VER` / `HYP`（台帳ごとに固定）
- `YYYYMMDD`：採番した日付
- `xxxx`：ランダムな16進4桁（`secrets.token_hex(2)`）

日付＋ランダム接尾辞なので、**独立したセッションが同じ日に採番しても衝突しない**。IDはレコードに書いた時点で固定し、後から変更しない（他のレコードが参照しているため）。

## 2. 採番方法

```sh
python3 scripts/new_id.py SRC            # 1件
python3 scripts/new_id.py EVD --count 3  # 3件
```

出力されたIDをそのままレコードに書く。既存の台帳を読んで重複を避けるので、通常は衝突しない。

**書き込み先は `state/<台帳名>.d/` の新しいシャードファイルである（2026-10-21 以降）。**

```sh
python3 scripts/new_ledger_shard.py evidence --create
# -> state/evidence.d/2026-10-21-3f9ac21b7d40.jsonl（空ファイルが作られる）
```

- `state/<台帳名>.jsonl` は**凍結ベース**であり、追記も編集もしない。既存レコードはそこに留まる。
- 1セッション／1作業バッチにつき1ファイル。書いたシャードは後から編集しない（訂正は新しいシャード＋記録）。
- ファイル名は `YYYY-MM-DD-<12桁hex>`。**日付だけでなく12桁のランダム要素が必須**（同日に並行するセッションが同名を作らないため）。
- 規則に合わない名前のファイルは読み手が拒否して報告する（黙って無視しない）。名前は `new_ledger_shard.py` に作らせるのが確実。
- 書誌スナップショットも同じ規則（`tests/fixtures/arxiv_metadata_snapshot.json` が凍結ベース、追加は `.../<YYYY-MM-DD>-<12桁hex>.json`）。`python3 scripts/new_ledger_shard.py arxiv_snapshot --create` で作る。
- 統合ビューの読み取りは `scripts/ledger_store.py` が一元化する。追記後に `python3 scripts/validate_state.py` を走らせ、緑を確認してから PR に出す。

背景と移行記録：`contributions/2026-10-21_ledger_sharding_migration.md`。

**採番は人間の承認なしに実行してよい。** 2026-10-21 に `docs/parallel-work-ownership.md` §2.1 で
`state/` を「統合役のみ」から「全セッション（追記のみ）」に変更したことに伴う。

- どのセッションも、台帳への追記とID採番を自律的に行ってよい。統合役への受け渡しは不要。
- 日付＋ランダム16進4桁なので、独立したセッションが同じ日に採番しても衝突しない（§1）。
- **採番したIDは変更しない。** 他のレコードが参照しているため（§1 の「IDはレコードに書いた時点で固定し、後から変更しない」）。
- **使わなかったIDは再利用しない。** 欠番のままにする。使い回すと別レコードを指すIDになる。

## 3. 既存レコードの扱い（据え置き）

2026-10-20 時点で存在した連番レコードは連番のまま残す。IDは参照されているため一括変更しない。

> **2026-10-20 追記**：連番レコードのうち16件（CLM-004/005/007、EVD-005/006/012/013/014、VER-008/009/014/016、VER-20261020-35a8/0d06/4dae、HYP-003）は、参照先のアーティファクトが `main` に存在せず新規チェックアウトから再検証できないため**台帳から除外**した。連番IDは**欠番のまま**とし、詰め直しも再利用もしない（欠番を埋めると別レコードを指すIDになる）。除外した16件の原文は `docs/archived-ledger-records-2026-10-20.md` に退避してある。

連番IDは**番号が凍結上限以下であれば**受理する。上限は `scripts/validate_state.py` の `LEGACY_MAX` に固定してある。

| 台帳 | 接頭辞 | 凍結上限 | 連番の現存件数 | 日付サフィックス | 合計 |
|---|---|---|---|---|---|
| sources | `SRC` | `SRC-004` | 4 | 7 | 11 |
| evidence | `EVD` | `EVD-014` | 9（5件除外で欠番） | 5 | 14 |
| claims | `CLM` | `CLM-007` | 4（3件除外で欠番） | 4 | 8 |
| verifications | `VER` | `VER-021` | 17（4件除外で欠番） | 8 | 25 |
| hypotheses | `HYP` | `HYP-003` | 2（1件除外で欠番） | 0 | 2 |

**上限を上げてはいけない。** 上限を超える連番（例：`EVD-015`）は「新規レコード」とみなされ、検証器がエラーにする。

**除外で生じた欠番も埋めてはいけない。** 連番IDは「その番号のレコード」を指す参照として各所に記録されている。欠番を詰め直すと、既存の参照が別のレコードを指すことになる。

```text
state/evidence.jsonl:15: ID 'EVD-015' extends the frozen sequential range
(max EVD-014); mint one with 'python3 scripts/new_id.py EVD' instead
```

## 4. 何を解決し、何を解決しないか

| 問題 | この方式 |
|---|---|
| 同一台帳への追記による **ID衝突**（add/add、union後の重複） | **解決**（接尾辞が独立） |
| 同一台帳への追記による **テキスト衝突** | **解決**（2026-10-21、方式B: 追記先を台帳ごとのシャードファイルに分けた。3ブランチ同時追記→順次マージで衝突0を実測。`contributions/2026-10-21_ledger_sharding_migration.md` §4） |
| 共有ファイル（`README.md`、`docs/`、`gitswarm/artifacts/`）の同時編集 | **未解決**（`docs/parallel-work-ownership.md` の所有マップで運用回避を試みるが、強制力はなく、規約を知らないセッションの編集は防げない）。唯一の例外は README／`docs/minimal-core-and-ci.md` の**現在値の数値行**で、`scripts/sync_doc_counts.py` により機械的に同期できる（衝突しても1行） |
| 誰が変更したかの識別 | **未解決**（全セッションが同一 git author のため原理的に不可） |

## 5. やらないこと

- ロール別のパス制限、レビューキュー、承認台帳は追加しない（`README.md` の凍結方針）。
- IDの自動採番をコミットフックやCIで強制しない。番号を採るのは作成時であり、事後に機械が埋めるものではない。
- `merge=union` は導入しない。テキスト衝突は消えるが、重複行を静かに残し、`ours`/`theirs` による消失を招くため（詳細は 2026-10-20 の検討記録）。
